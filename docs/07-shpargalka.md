## Короткие ответы

### Общая теория

**[1.1](01-teoriya.md#11-что-такое-индекс-какие-задачи-он-решает-и-чем-за-это-приходится-платить) Что такое индекс, задачи и цена.**
Отдельная отсортированная структура (обычно B-дерево) со ссылками на строки. Ускоряет поиск, диапазоны, сортировку, соединения, проверку уникальности, сужает блокировки. Цена: медленнее запись (правятся все индексы), место на диске и в кэше, обслуживание (перестроение, статистика, VACUUM).

**[1.2](01-teoriya.md#12-как-устроено-b-дерево-почему-поиск-логарифмический) B-дерево.**
Корень → промежуточные (только маршруты) → листья (все ключи по порядку, связаны списком). Сбалансировано, на странице 8 КБ сотни ключей → глубина `log_B(N)`: 3 уровня ≈ 27 млн строк. Листья в списке → диапазоны и `ORDER BY` без сортировки.

**[1.3](01-teoriya.md#13-что-такое-селективность-и-кардинальность) Селективность и кардинальность.**
Селективность — доля строк под условием. Кардинальность — число строк (на выходе шага плана или различных значений в колонке). Оценка = строки × селективность; берётся из статистики. Устарела статистика → плохой план.

**[1.4](01-teoriya.md#14-почему-индекс-по-малоселективному-полю-может-не-использоваться-на-примере-булева-поля) Индекс по малоселективному (булеву) полю.**
Через некластерный индекс каждая строка = случайное чтение таблицы; при большой доле строк последовательное сканирование дешевле → оптимизатор берёт Scan. Индекс только мешает записи. Исключения: перекос (ищем редкое), фильтруемый/частичный индекс, покрывающий, составной.

**[1.5](01-teoriya.md#15-как-порядок-колонок-в-составном-индексе-влияет-на-его-применимость-правило-левого-префикса) Порядок колонок, левый префикс.**
`(A,B,C)` сортирован как справочник «Фамилия, Имя, Отчество». Поиск — по `A`, `A+B`, `A+B+C`; по `B` без `A` — нет (кроме skip scan в PG 18). Равенства — первыми, диапазон — последним. Порядок колонок = какой `ORDER BY` без сортировки. В 1С — порядок измерений регистра.

**[1.6](01-teoriya.md#16-что-такое-покрывающий-индекс-и-зачем-нужны-включённые-столбцы-include) Покрывающий индекс, INCLUDE.**
Покрывающий — все нужные запросу поля в индексе, в таблицу не ходим (нет Key Lookup, Index Only Scan). `INCLUDE` — поля только в листьях: не для поиска, не влияют на уникальность и лимиты ключа, верхние уровни компактные. В PG Index Only Scan зависит от карты видимости (VACUUM).

**[1.7](01-teoriya.md#17-что-такое-уникальный-индекс-и-чем-он-отличается-от-ограничения-уникальности) Уникальный индекс vs ограничение.**
Ограничение — логическое правило схемы, индекс — механизм проверки (создаётся под ограничение автоматически). Индекс гибче: `INCLUDE`, фильтр `WHERE`. NULL: MS SQL — один NULL; PG — сколько угодно (или `NULLS NOT DISTINCT` с PG 15).

**[1.8](01-teoriya.md#18-как-индексы-влияют-на-блокировки-и-взаимоблокировки) Индексы и блокировки.**
С индексом блокируются только найденные строки. Без индекса — сканирование → много блокировок → эскалация до таблицы (MS SQL, ~5000 блокировок); в SERIALIZABLE — диапазон = вся таблица (key-range в MS SQL, SSI в PG). Дедлоки: индексы сокращают время блокировок, но разный порядок обхода и повышение S→X их провоцируют.

### MS SQL Server

**[2.1](02-mssql.md#21-каковы-ограничения-на-ключ-индекса-байты-число-колонок) Лимиты ключа.**
MS SQL 2016+: 900 байт кластерный, 1700 некластерный, 32 колонки; `INCLUDE` вне лимитов (до 1023 колонок), `(max)` в ключ нельзя. PG: 32 колонки, запись ~2700 байт. В 1С: символ = 2 байта, Ссылка = 16; кластерный индекс регистра сведений = все измерения ≤ 900 байт.

**[2.2](02-mssql.md#22--что-такое-fill-factor-и-зачем-может-потребоваться-его-менять-что-такое-page-split) ★ Fill factor и page split.**
Page split — вставка в полную страницу → новая страница, половина строк переезжает → две полупустые страницы, фрагментация, лишний журнал. Fill factor — % заполнения листьев при создании/REBUILD (по умолчанию 100). Снижают (90–70) при вставках в середину (GUID, коды, строки) и расширяющих UPDATE. Цена: индекс больше, чтение медленнее. При возрастающем ключе — бесполезно.

**[2.3](02-mssql.md#23-что-такое-фрагментация-и-как-её-измерить-чем-reorganize-отличается-от-rebuild-и-как-изменился-подход-microsoft-к-порогам) Фрагментация, REORGANIZE/REBUILD, пороги.**
Логическая (страницы не по порядку) и низкая плотность. `sys.dm_db_index_physical_stats`. REORGANIZE — листья, онлайн, прерываемый, без статистики. REBUILD — заново, офлайн/онлайн (Enterprise), обновляет статистику индекса. Microsoft: не «5/30%», а по измеренному эффекту; часто помогает не дефрагментация, а свежая статистика.

**[2.4](02-mssql.md#24-что-показывают-sysdm_db_index_usage_stats-и-sysdm_db_missing_index_-ограничения-рекомендаций-по-недостающим-индексам) usage_stats и missing_index.**
usage_stats — seeks/scans/lookups против updates для существующих индексов. missing_index — колонки равенства/неравенства/include и выгода. Обе в памяти, сбрасываются. Missing: не учитывает запись, не даёт порядок колонок, только обычные некластерные, дубли, лимит 600 групп — применять с консолидацией и головой.

**[2.5](02-mssql.md#25-чем-columnstore-отличается-от-rowstore-и-для-каких-нагрузок-он-подходит) Columnstore vs rowstore.**
Rowstore — строки целиком (OLTP). Columnstore — группы строк по ~1 млн, каждая колонка отдельно и сжата; читаются только нужные колонки, batch mode, segment elimination; мелкие вставки — в deltastore. Для аналитики; некластерный columnstore — аналитика поверх OLTP.

**[2.6](02-mssql.md#26-что-такое-фильтруемые-индексы-и-сжатие-данных-и-когда-они-полезны) Фильтруемые индексы и сжатие.**
Фильтруемый — индекс по части строк (`WHERE`): NULL-колонки, редкие значения, горячие данные; меньше, точнее статистика; осторожно с параметризованными запросами. Сжатие ROW/PAGE — меньше IO и памяти за счёт CPU, для больших таблиц.

### PostgreSQL

**[3.1](03-postgresql.md#31-какие-типы-индексов-есть-в-postgresql-и-для-чего-каждый) Типы индексов.**
B-tree (по умолчанию, диапазоны, сортировка, единственный для UNIQUE), Hash (только `=`), GiST (геометрия, диапазоны, KNN, EXCLUDE), SP-GiST (префиксы, IP, точки), GIN (элементы: JSONB, массивы, полнотекст, триграммы), BRIN (min/max блоков для огромных упорядоченных таблиц). 1С — только B-tree.

**[3.2](03-postgresql.md#32-почему-в-postgresql-нет-кластерного-индекса-в-понимании-ms-sql-и-что-делает-cluster) Нет кластерного индекса; CLUSTER.**
Таблица всегда куча, индексы вторичные, ссылаются на `ctid`; держать порядок при MVCC слишком дорого. `CLUSTER` — однократная перезапись в порядке индекса, ACCESS EXCLUSIVE, порядок не поддерживается. Цель — корреляция → дешевле диапазоны.

**[3.3](03-postgresql.md#33-как-mvcc-влияет-на-индексы-что-такое-hot-обновления-и-раздувание-bloat) MVCC, HOT, bloat.**
UPDATE = новая версия по новому `ctid` → запись во все индексы. HOT: индексированные колонки не менялись + место на той же странице → индексы не трогаем, цепочка версий, внутристраничная очистка. Bloat — мёртвые версии и пустота: долгие транзакции, отставший autovacuum, нет места для HOT.

**[3.4](03-postgresql.md#34-что-значит-fillfactor-в-postgresql-для-таблицы-и-для-индекса-и-чем-он-отличается-от-ms-sql) fillfactor PG vs MS SQL.**
PG: у таблицы (100, ради HOT) и у индекса (B-tree 90, ради split). MS SQL: только индексы, 100, ради split. Применяется при заполнении «с нуля».

**[3.5](03-postgresql.md#35-какова-роль-vacuum-и-autovacuum-в-обслуживании-индексов-чем-отличаются-reindex-и-reindex-concurrently) VACUUM; REINDEX vs CONCURRENTLY.**
VACUUM: собирает мёртвые TID → удаляет их из всех индексов → освобождает место в таблице → обновляет карту видимости (нужна Index Only Scan). Файлы не сжимает. Autovacuum — по порогу `50 + 0,2 × строк`. REINDEX — блокирует запись в таблицу и сам индекс. CONCURRENTLY (PG 12+) — без блокировки записи, медленнее, не в транзакции, при сбое INVALID-индекс.

**[3.6](03-postgresql.md#36-как-отличить-фрагментацию-индекса-от-раздувания-в-postgresql) Фрагментация vs раздувание.**
Bloat — «пусто внутри страниц» (таблицы и индексы); фрагментация — «листья B-tree не по порядку». `pgstattuple` (`tuple_percent`), `pgstatindex` (`avg_leaf_density`, `leaf_fragmentation`).

**[3.7](03-postgresql.md#37-как-найти-неиспользуемые-индексы-и-проблемные-запросы-pg_stat_user_indexes-explain-analyze-pg_stat_statements) Мониторинг.**
`pg_stat_user_indexes.idx_scan` → неиспользуемые (кроме уникальных; за полный цикл). `pg_stat_statements` (`total_exec_time`) → тяжёлые запросы. `EXPLAIN (ANALYZE, BUFFERS)` → оценка vs факт, методы доступа, `Rows Removed by Filter`, сброс на диск.

### Секционирование

**[4.1](04-sekcionirovanie.md#41--в-чём-особенность-совместной-работы-индексов-и-секционирования-в-ms-sql-выровненные-индексы-switch-partition-elimination) ★ Индексы и секционирование в MS SQL.**
Выровненный индекс = дерево на каждую секцию (по умолчанию). Даёт `SWITCH` (только если все индексы выровнены), обслуживание по секциям, partition elimination. Уникальный ключ обязан содержать колонку секционирования. Без условия по ней — Seek в каждой секции, OLTP медленнее.

**[4.2](04-sekcionirovanie.md#42-как-секционирование-влияет-на-операцию-seek-что-такое-partition-elimination) Partition elimination.**
По условию на ключ секционирования читаются только нужные секции (при планировании или выполнении). Нет условия → Seek по всем секциям, `Scan count` = числу секций.

**[4.3](04-sekcionirovanie.md#43-пример-скользящего-окна-sliding-window-на-t-sql-split-merge-switch) Скользящее окно.**
`SWITCH` старой секции в архив → `MERGE RANGE` пустой границы → `NEXT USED` + `SPLIT RANGE` новой. Мгновенно, только если секции пусты; пустые секции по краям; индексы выровнены.

**[4.4](04-sekcionirovanie.md#44-глобальные-и-локальные-индексы-при-секционировании-что-есть-в-ms-sql-и-postgresql) Глобальные и локальные.**
Локальный — дерево на секцию (MS SQL и PG). Глобальный — одно дерево (только MS SQL): уникальность по любому полю и один поиск, но мешает SWITCH.

**[4.5](04-sekcionirovanie.md#45-как-устроено-секционирование-в-postgresql-почему-там-нет-глобальных-индексов-и-как-это-влияет-на-уникальность) Секционирование в PG.**
Декларативное RANGE/LIST/HASH; секция — отдельная таблица (куча); индекс ссылается на `ctid` своей кучи → только локальные индексы → PK/UNIQUE обязаны включать ключ секционирования. Pruning при планировании и выполнении; DETACH/ATTACH вместо SWITCH.

### 1С

**[5.1](05-1c.md#51-какие-индексы-платформа-создаёт-автоматически-для-справочников-документов-и-регистров) Индексы платформы.**
Справочник: кластерный по Ссылке; Код+Ссылка; Наименование+Ссылка; Реквизит+Ссылка (с доп. упорядочиванием — +Код/Наименование). Документ: Ссылка; Дата+Ссылка; Номер+Ссылка; Реквизит+Ссылка (с доп. упорядочиванием — +Дата). Регистр сведений: кластерный по измерениям (+Период). Регистр накопления: движения — Период+Регистратор+НомерСтроки и Регистратор+НомерСтроки; итоги — Период+измерения. Порядок — как в конфигураторе.

**[5.2](05-1c.md#52--какие-рекомендации-можно-дать-при-создании-индексов-объектов-метаданных-в-1с) ★ Рекомендации по индексам метаданных.**
Индексировать только используемое и селективное (не Булево, не первое измерение). Измерения: первыми — частые и селективные отборы, подряд, остальным — «Индексировать»/«Ведущее». Строки — минимальной длины (2 байта/символ + 16 на Ссылку; ≤ 900 байт в кластерном индексе регистра сведений). Составные типы — минимум; через точку — только `ВЫРАЗИТЬ`. Доп. упорядочивание — для динамических списков. Отборы — в параметры виртуальных таблиц.

**[5.3](05-1c.md#53-какие-особенности-есть-у-1с-на-postgresql-mvarcharmchar-регистронезависимость-online_analyze) 1С на PostgreSQL.**
Сборка PG для 1С: `mvarchar`/`mchar` — строки как в MS SQL, регистронезависимо, обычный индекс работает без `lower()`. `online_analyze` — синхронный ANALYZE временных таблиц (autovacuum их не видит). `plantuner.fix_empty_table` — против плохих планов на пустых таблицах.

**[5.4](05-1c.md#54-основные-различия-в-организации-индексов-ms-sql-и-postgresql-которые-нужно-учитывать-в-1с) Различия MS SQL и PG для 1С.**
Кластерная таблица vs куча; UPDATE на месте vs новая версия (bloat, VACUUM); REBUILD/REORGANIZE vs VACUUM/REINDEX CONCURRENTLY; nvarchar CI vs mvarchar; статистика временных таблиц — online_analyze. Набор индексов платформы — тот же.

### Обслуживание и диагностика

**[6.1](06-obsluzhivanie-diagnostika.md#61-каков-регламент-обслуживания-индексов-и-статистики-для-баз-1с-на-ms-sql-и-на-postgresql) Регламент.**
MS SQL: статистика ежедневно + FREEPROCCACHE; индексы выборочно в окно. PG: настроенный autovacuum, контроль долгих транзакций, online_analyze, REINDEX CONCURRENTLY / pg_repack по факту раздувания. «Тестирование и исправление» — монопольно, для регламента не используют.

**[6.2](06-obsluzhivanie-diagnostika.md#62-как-найти-медленный-запрос-и-связанный-с-ним-индекс-технологический-журнал-цуп-profiler--extended-events-pg_stat_statements) Как найти медленный запрос и индекс.**
ТЖ (DBMSSQL/DBPOSTGRS + `<plansql/>` + контекст), ЦУП, Extended Events/Profiler/Query Store, pg_stat_statements/лог/auto_explain → план → имена индексов → метаданные через `ПолучитьСтруктуруХраненияБазыДанных()`.

**[6.3](06-obsluzhivanie-diagnostika.md#63-кейс-отчёт-по-регистру-тормозит-порядок-диагностики-и-варианты-решения-через-индексы) Кейс: тормозит отчёт по регистру.**
Где время (код/СУБД) → запрос и план → сканирования, Key Lookup, оценка vs факт → текст запроса. Решения: отбор в параметры ВТ; порядок измерений / «Индексировать»; временная таблица + `ИНДЕКСИРОВАТЬ ПО`; агрегаты и актуальные итоги; статистика; обслуживание индексов.

## MS SQL Server и PostgreSQL — сравнение одной таблицей

| Тема | MS SQL Server | PostgreSQL |
|---|---|---|
| Организация таблицы | Кластерный индекс (B-дерево со строками) или куча | Всегда куча |
| Ссылка из некластерного индекса | Ключ кластерного индекса / RID | `ctid` |
| UPDATE | На месте | Новая версия строки (MVCC) |
| Оптимизация UPDATE для индексов | Не нужна: индексы не трогаются, если их колонки не менялись | HOT-обновления |
| Типы индексов | B-tree (rowstore), columnstore, hash (In-Memory), XML, spatial, full-text | B-tree, Hash, GiST, SP-GiST, GIN, BRIN |
| Покрывающие индексы | `INCLUDE` | `INCLUDE` (PG 11+) |
| Частичные индексы | Фильтруемые (`WHERE`, простые условия) | Частичные (`WHERE`, любые immutable-выражения) |
| Индексы по выражению | Через вычисляемую колонку | Напрямую: `CREATE INDEX ON t (lower(name))` |
| Fill factor | Индексы, по умолчанию 100 | Таблицы 100, B-tree 90 |
| Дефрагментация | `REORGANIZE` / `REBUILD` | `REINDEX` / `REINDEX CONCURRENTLY`, `pg_repack` |
| Онлайн-перестроение | `ONLINE = ON` (Enterprise), `RESUMABLE` (2017+) | `REINDEX CONCURRENTLY` (12+), `CREATE INDEX CONCURRENTLY` |
| Очистка | Не требуется (версии snapshot — в tempdb) | `VACUUM` / autovacuum |
| Статистика | `UPDATE STATISTICS`, гистограмма до 200 шагов | `ANALYZE`, `pg_stats`, `default_statistics_target` |
| Использование индексов | `sys.dm_db_index_usage_stats` | `pg_stat_user_indexes` |
| Недостающие индексы | `sys.dm_db_missing_index_*` | Встроенного нет (`hypopg`, анализ планов) |
| Тяжёлые запросы | Query Store, `sys.dm_exec_query_stats`, XE | `pg_stat_statements`, `auto_explain` |
| Фрагментация/раздувание | `sys.dm_db_index_physical_stats` | `pgstattuple`, `pgstatindex` |
| Секционирование и индексы | Выровненные и невыровненные | Только локальные |
| Эскалация блокировок | Есть (~5000 блокировок → таблица) | Строковых — нет |
| NULL в уникальном индексе | Один NULL | Сколько угодно (или `NULLS NOT DISTINCT`, 15+) |

## Числа, которые стоит помнить

| Что | Значение |
|---|---|
| Размер страницы | 8 КБ (обе СУБД) |
| Глубина B-дерева | 3–4 уровня для десятков миллионов строк |
| Лимит ключа MS SQL | 900 байт (кластерный), 1700 (некластерный), 32 колонки |
| Лимит PG | ~2700 байт на запись B-tree, 32 колонки |
| Fill factor по умолчанию | MS SQL 100 (0); PG: таблица 100, B-tree 90, Hash 75, GiST 90, SP-GiST 80 |
| Классические пороги фрагментации | 5–30% REORGANIZE, > 30% REBUILD (устаревший подход) |
| Маленький индекс, который не обслуживают | < ~1000 страниц |
| Эскалация блокировок MS SQL | ~5000 блокировок на объект в одном операторе |
| Missing index DMV | не больше 600 групп |
| Rowgroup columnstore | до 1 048 576 строк |
| Autovacuum по умолчанию | `50 + 0,2 × строк` мёртвых строк; ANALYZE — `50 + 0,1 × строк` |
| `random_page_cost` / `seq_page_cost` (PG) | 4 / 1 (на SSD ставят ~1,1) |
| BRIN | по умолчанию 128 страниц на диапазон |
| Строка 1С в индексе | 2 байта на символ; Ссылка — 16 байт |

## Словарик

| Термин | Смысл |
|---|---|
| Seek | Поиск по индексу со спуском от корня |
| Scan | Просмотр индекса или таблицы (целиком или диапазон) |
| Key Lookup / RID Lookup | Обращение за строкой в кластерный индекс / кучу по ссылке из некластерного индекса (MS SQL) |
| Index Only Scan | Чтение только индекса без таблицы (PG) |
| Bitmap Scan | Сбор ссылок из индекса в битовую карту и чтение страниц таблицы по порядку (PG) |
| Heap | Куча — таблица без порядка строк |
| TID / ctid | Физический адрес версии строки в PG (страница, позиция) |
| Page split | Расщепление полной страницы при вставке |
| Fill factor | Процент заполнения страниц при создании/перестроении |
| HOT | Heap-Only Tuple — обновление без записи в индексы (PG) |
| Bloat | Раздувание — мёртвые версии и пустота в файлах (PG) |
| Visibility map | Карта видимости страниц — нужна для Index Only Scan (PG) |
| Aligned index | Выровненный (локальный) индекс на секционированной таблице |
| Partition elimination / pruning | Отсечение секций |
| Rowgroup / segment / deltastore | Части columnstore |
| Tipping point | Доля строк, при которой оптимизатор переходит от индекса к сканированию |
