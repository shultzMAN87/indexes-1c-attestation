# Глава 5. Индексы в 1С:Предприятии

[← Глава 4. Секционирование](04-sekcionirovanie.md) · [Оглавление](../README.md) · [Глава 6. Обслуживание и диагностика →](06-obsluzhivanie-diagnostika.md)

Главное правило 1С: **структурой базы данных управляет платформа**. Разработчик влияет на индексы только через свойства метаданных (порядок измерений, «Индексировать», «Ведущее», длина строк, состав типов) и через текст запросов. Индексы, созданные вручную в СУБД, платформа не знает: они могут пропасть при реструктуризации или помешать обновлению конфигурации.

---

## 5.1. Какие индексы платформа создаёт автоматически для справочников, документов и регистров

> **Коротко.** Для объектных таблиц (справочники, документы) — кластерный индекс по **Ссылке** и индексы «поле + Ссылка»: по коду, наименованию (справочники), по дате и номеру (документы), по каждому реквизиту с признаком «Индексировать» (при доп. упорядочивании — «Реквизит + Код/Наименование/Дата + Ссылка»). Для регистров сведений — кластерный индекс по **измерениям** (у периодических — с Периодом, порядок зависит от режима совместимости) и индексы по измерениям/реквизитам с «Индексировать»/«Ведущее». Для регистров накопления: таблица движений — по **Периоду + Регистратору + НомеруСтроки** и по **Регистратору + НомеруСтроки**; таблица итогов — по **Периоду + всем измерениям**. Порядок полей во всех этих индексах повторяет порядок измерений в конфигураторе.

> ℹ️ Состав индексов ниже — по «Настольной книге 1С:Эксперта по технологическим вопросам» и материалам ИТС «Индексы таблиц базы данных». Он может отличаться в зависимости от версии платформы и режима совместимости, поэтому на реальной базе проверяйте через [`ПолучитьСтруктуруХраненияБазыДанных()`](#как-узнать-физические-имена-таблиц-и-индексов).
>
> Слово «кластерный» относится к MS SQL. В PostgreSQL тот же набор индексов создаётся как обычные B-tree поверх кучи.

### Справочник (`_ReferenceN`)

| Индекс | Когда создаётся |
|---|---|
| **Ссылка** — кластерный | Всегда |
| Код + Ссылка | Длина кода > 0 |
| Наименование + Ссылка | Длина наименования > 0 |
| Родитель + … + Ссылка | Справочник иерархический |
| Владелец + … + Ссылка | Справочник подчинённый |
| Реквизит + Ссылка | «Индексировать» = *Индексировать* |
| Реквизит + Код + Ссылка | *Индексировать с доп. упорядочиванием*, основное представление «В виде кода» |
| Реквизит + Наименование + Ссылка | *Индексировать с доп. упорядочиванием*, основное представление «В виде наименования» |
| Реквизит | Справочник входит в **критерий отбора** через этот реквизит |

### Документ (`_DocumentN`)

| Индекс | Когда создаётся |
|---|---|
| **Ссылка** — кластерный | Всегда |
| Дата + Ссылка | Всегда |
| Номер + Ссылка (с учётом периодичности номера) | Длина номера > 0 |
| Реквизит + Ссылка | *Индексировать* |
| Реквизит + Дата + Ссылка | *Индексировать с доп. упорядочиванием* |
| Реквизит | Входит в критерий отбора |

**Табличные части** (`_DocumentN_VTM`, `_ReferenceN_VTM`): кластерный индекс по Ссылке на владельца + служебному ключу строки.

### Регистр сведений (`_InfoRgN`)

**Непериодический, независимый:**
- **кластерный:** Измерение1 + Измерение2 + … (все измерения в порядке конфигуратора);
- для измерения N с «Индексировать» или «Ведущее» (если оно не первое и не единственное): ИзмерениеN + Измерение1 + …;
- для реквизита/ресурса с «Индексировать»: Реквизит + Измерение1 + …;
- служебный индекс по короткому ключу записи (`SimpleKey`).

**Периодический, независимый:**

| | 8.2 и режим совместимости 8.2 | 8.3 без режима совместимости |
|---|---|---|
| Кластерный | Период + Измерения | Измерения + Период |
| По измерению N с «Индексировать» или «Ведущее» (не единственному) | ИзмерениеN + Период + Измерение1 + … | ИзмерениеN + Период + Измерение1 + … |

**Ведущее измерение:** индекс по нему создаётся **всегда**, поэтому свойство «Индексировать» у ведущего измерения недоступно. Индексировать **ресурсы** можно только у регистра сведений; реквизиты — у регистров всех видов.

**Подчинённый регистратору:** индекс Регистратор + НомерСтроки (у непериодического — кластерный); при периодичности «По позиции регистратора» — кластерный Период + Регистратор + НомерСтроки и индекс Измерения + Период + Регистратор + НомерСтроки.

Если включены итоги «Срез последних» / «Срез первых», создаются отдельные таблицы срезов (`_InfoRgSLN`, `_InfoRgSFN`) со своими индексами по измерениям.

> ⚠️ Таблица периодического регистра сведений исправлена: в прежней редакции для 8.3 указывался «второй индекс Период + Измерения». В описаниях структуры хранения для 8.3 такого обязательного индекса нет — проверяйте на своей базе.

### Регистр накопления

| Таблица | Индекс |
|---|---|
| **Движения** (`_AccumRgN`) | **кластерный:** Период + Регистратор + НомерСтроки |
| | Регистратор + НомерСтроки |
| | Измерение/реквизит с «Индексировать» + Период + Регистратор + НомерСтроки |
| **Итоги** вида «Остатки» (`_AccumRgTN`) | **кластерный:** Период + Измерение1 + … + ИзмерениеN [+ Splitter при разделении итогов] |
| | Измерение с «Индексировать» + Период |
| **Итоги** вида «Обороты» (`_AccumRgTN`) | **кластерный:** Период + Измерения [+ Splitter] |
| | Измерение с «Индексировать» + Период |

Отсюда два вывода, которые нужны для [5.2](#52--какие-рекомендации-можно-дать-при-создании-индексов-объектов-метаданных-в-1с):
1. Таблица итогов **уже** отсортирована по первому измерению (после периода) → «Индексировать» у первого измерения не нужно.
2. Отбор по измерению, стоящему не первым, основной индекс итогов эффективно не использует.

### Разделение данных и разделение итогов

- Если в конфигурации есть общий реквизит-разделитель, его колонка (или хеш нескольких разделителей) добавляется **первой** в индексы разделённых таблиц. Это расходует часть лимита ключа (см. [2.1](02-mssql.md#21-каковы-ограничения-на-ключ-индекса-байты-число-колонок)).
- Если у регистра разрешено **разделение итогов**, колонка `Splitter` добавляется **последней** в индексы таблиц итогов (см. [5.10](#510-что-такое-разделение-итогов-и-как-оно-влияет-на-индексы-таблиц-итогов)).

### Как узнать физические имена таблиц и индексов

План запроса и журналы СУБД оперируют именами вида `_AccumRg1234`, `_Document56_VT78`, `_Fld910`, `_AccumRg1234_ByPeriod_TRN`. Сопоставить их с метаданными:

```bsl
// Выполнить на сервере (например, во внешней обработке или в режиме отладки)
Структура = ПолучитьСтруктуруХраненияБазыДанных(, Истина); // Истина — имена в терминах СУБД
Для Каждого Строка Из Структура Цикл
    Если СтрНайти(Строка.ИмяТаблицыХранения, "_AccumRg1234") > 0 Тогда
        Сообщить(Строка.Метаданные + " / " + Строка.Назначение + " → " + Строка.ИмяТаблицыХранения);
        Для Каждого Индекс Из Строка.Индексы Цикл
            Сообщить("   индекс: " + Индекс.ИмяИндексаХранения);
        КонецЦикла;
    КонецЕсли;
КонецЦикла;
```

В 1С:ЦУП сопоставление выполняется автоматически.

Чего `ПолучитьСтруктуруХраненияБазыДанных()` **не показывает:** кластерный индекс по Ссылке у объектных таблиц, поле-хеш общих реквизитов-разделителей в начале индексов, индекс `SimpleKey` регистра сведений. Полный состав — только в среде СУБД.

> **Запомнить:** объект → кластерный по Ссылке + «поле + Ссылка». Регистр → индексы по измерениям **в порядке конфигуратора**; у регистра накопления движения по Периоду и Регистратору, итоги по Периоду + измерениям.

## 5.2. ★ Какие рекомендации можно дать при создании индексов объектов метаданных в 1С

> **Коротко.** (1) Индексировать **только то, по чему реально отбирают** и что достаточно селективно: не `Булево`, не статусы из 2–3 значений, не то, что уже индексирует платформа (первое измерение регистра). (2) **Порядок измерений** регистра: первыми — те, по которым отбирают чаще всего и которые наиболее селективны; для отборов по остальным — «Индексировать» / «Ведущее». (3) **Строки:** неограниченные не индексируются; длину индексируемых строк и строковых измерений делать минимально нужной и учитывать лимит ключа (2 байта на символ + 16 байт на Ссылку; сумма измерений регистра сведений ≤ 900 байт в MS SQL). (4) **Составные типы:** минимум типов; составное поле — это до 7 колонок в индексе; не обращаться к нему через точку без `ВЫРАЗИТЬ`. (5) **Доп. упорядочивание** — для реквизитов, по которым отбирают в динамических списках с сортировкой по коду/наименованию/дате. (6) Помнить цену: каждый индекс замедляет запись и удлиняет реструктуризацию.

### 1. Выбор реквизитов для индексирования

| Делать | Не делать |
|---|---|
| Индексировать реквизит, по которому есть **частые отборы и соединения** в запросах, отчётах, динамических списках | Индексировать «на всякий случай» |
| Проверять селективность: значение должно отбирать **малую долю** строк | Индексировать `Булево`, `ПометкаУдаления`, перечисления из 2–3 значений (исключение — сильный перекос и поиск редкого значения, см. [1.4](01-teoriya.md#14-почему-индекс-по-малоселективному-полю-может-не-использоваться-на-примере-булева-поля)) |
| Использовать то, что платформа уже создаёт (Ссылка, Код, Наименование, Дата, Номер, первое измерение) | Ставить «Индексировать» у **первого измерения** регистра — индекс по нему уже есть |
| Снимать лишние галочки, найденные по статистике использования ([2.4](02-mssql.md), [3.7](03-postgresql.md)) | Добавлять индексы средствами СУБД в обход конфигуратора |

Цена каждого индекса — замедление записи (проведение документов, запись регистров), рост базы и **время реструктуризации** при обновлении конфигурации.

### 2. «Индексировать» или «Индексировать с доп. упорядочиванием»

| Вариант | Индекс справочника | Индекс документа | Когда выбирать |
|---|---|---|---|
| Индексировать | Реквизит + Ссылка | Реквизит + Ссылка | Отбор/соединение по реквизиту в запросах |
| С доп. упорядочиванием | Реквизит + Код/Наименование + Ссылка | Реквизит + Дата + Ссылка | Динамический список **с отбором** по реквизиту и **сортировкой** по основному представлению (коду, наименованию) или дате — индекс отдаёт строки уже в нужном порядке |

Доп. упорядочивание делает индекс шире — без нужды его не используют.

### 3. Порядок измерений в регистрах

Индексы регистров повторяют порядок измерений → работает правило левого префикса ([1.5](01-teoriya.md#15-как-порядок-колонок-в-составном-индексе-влияет-на-его-применимость-правило-левого-префикса)).

**Пример.** Регистр накопления «ТоварыНаСкладах» с измерениями `Склад, Номенклатура, Характеристика`. Кластерный индекс итогов: `Период + Склад + Номенклатура + Характеристика`.

| Запрос | Использует индекс эффективно? |
|---|---|
| Остатки по складу | Да: `Период + Склад` — левый префикс |
| Остатки по складу и номенклатуре | Да |
| Остатки номенклатуры по **всем** складам | Нет: `Склад` пропущен → просмотр всех складов |

**Решения:**
- если отборы по номенклатуре без склада частые — поставить `Номенклатура` **первой**;
- или установить у `Номенклатура` свойство **«Индексировать»** → платформа создаст индекс `Номенклатура + Период` (в итогах) и `Номенклатура + Период + Регистратор + НомерСтроки` (в движениях);
- «Ведущее» у измерения регистра сведений тоже даёт индекс по этому измерению.

**Общие правила:**
- первым — измерение, по которому отбирают **чаще всего** и которое **наиболее селективно**;
- измерения, по которым отбирают вместе, — **подряд**, без «дыр»;
- поля, по которым не нужно получать итоги и отбирать, делать **реквизитами**, а не измерениями (меньше итоговых записей и короче индексы);
- менять порядок измерений в работающей базе = реструктуризация больших таблиц — планировать заранее.

### 4. Длина строк

- Строки **неограниченной** длины (`nvarchar(max)` / `mvarchar` без длины) не индексируются: «Индексировать» для них недоступно, по ним нельзя эффективно отбирать, группировать и сравнивать на равенство в запросе.
- Индексируемая строка длиной N символов занимает в ключе **2·N байт**, плюс 16 байт Ссылки. Лимиты: MS SQL — 1700 байт некластерный, **900 байт кластерный**; PostgreSQL — ~2700 байт.
- **Регистр сведений:** все измерения входят в кластерный индекс → сумма длин строковых измерений ×2 + остальные поля должна уложиться в **900 байт** (MS SQL). Иначе индекс создастся с предупреждением, а ошибка случится при записи длинного значения.
- Вывод: строковые реквизиты для отборов и строковые измерения — **такой длины, какая реально нужна** (артикул — 25–50, а не 1024). Проще всего — ссылочные типы вместо строковых измерений.

> ⚠️ **Поправка к ответу NotebookLM:** правила «не более 100–150 символов» нет — ограничение вытекает из лимита ключа СУБД и считается, как показано выше.

### 5. Составные типы

Реквизит составного типа хранится **несколькими колонками**:

| Колонка | Что хранит |
|---|---|
| `_FldN_TYPE` | Вид значения (ссылка, число, строка, дата, булево, неопределено) |
| `_FldN_RTRef` | Номер таблицы ссылочного типа (4 байта) |
| `_FldN_RRRef` | Сама ссылка (16 байт) |
| `_FldN_N`, `_FldN_S`, `_FldN_T`, `_FldN_L` | Число, строка, дата, булево — если такие типы входят в состав |

Поэтому:
- индекс по составному реквизиту содержит **все** эти колонки — он шире;
- **минимизировать состав типов**: «ЛюбаяСсылка» и «ДокументСсылка» (любой документ) — только если без этого никак;
- **не обращаться через точку** к полям составного типа: `Регистратор.Номер` порождает `LEFT JOIN` ко **всем** таблицам документов, входящих в тип (и к таблицам RLS). Использовать `ВЫРАЗИТЬ(Регистратор КАК Документ.РеализацияТоваровУслуг).Номер` — соединение будет одно;
- если реквизит составного поля (дата, организация документа-регистратора) постоянно нужен в отчётах — **денормализовать**: хранить его отдельным реквизитом регистра и заполнять при записи.

### 6. Условия в запросах, которые «ломают» индекс

Даже правильный индекс не поможет, если условие не позволяет по нему искать:

| Плохо | Почему | Лучше |
|---|---|---|
| `ГДЕ Остатки.Склад = &Склад` после `ОстаткиИОбороты()` | Сначала собираются остатки по всем складам, потом фильтр | `Остатки(&Дата, Склад = &Склад)` — отбор в **параметрах виртуальной таблицы** |
| `ПОДОБНО "%текст%"` | Ведущий `%` — нет левого префикса | `ПОДОБНО "текст%"` или полнотекстовый поиск |
| `ГОД(Дата) = 2024`, `ПОДСТРОКА(...)` | Функция над полем — индекс по полю не применим | `Дата МЕЖДУ &Начало И &Конец` |
| `А = 1 ИЛИ Б = 2` | Сложно для оптимизатора, часто сканирование | Два запроса через `ОБЪЕДИНИТЬ ВСЕ` |
| `СОЕДИНЕНИЕ` с подзапросом / виртуальной таблицей | Оптимизатор плохо оценивает число строк подзапроса | Сначала **временная таблица** с `ИНДЕКСИРОВАТЬ ПО` полям соединения |
| `Поле.Реквизит.Реквизит` от составного типа | Неявные соединения со множеством таблиц | `ВЫРАЗИТЬ(...)`, денормализация |

**`ИНДЕКСИРОВАТЬ ПО`** во временной таблице полезно, когда она **большая** и используется в соединении или отборе по этим полям. Для временной таблицы из десятков строк индекс бесполезен — его построение дороже выгоды.

> **Запомнить (шесть пунктов для ответа):** индексировать только нужное и селективное; порядок измерений — по отборам; «Индексировать»/«Ведущее» для остальных; строки — короткие (считать байты); составные типы — минимум, `ВЫРАЗИТЬ` вместо точки; доп. упорядочивание — для динамических списков.

## 5.3. Какие особенности есть у 1С на PostgreSQL: `mvarchar`/`mchar`, регистронезависимость, `online_analyze`

> **Коротко.** Платформа исторически рассчитана на поведение MS SQL, поэтому 1С использует **специальную сборку PostgreSQL** (от 1С или Postgres Pro для 1С). В ней есть типы **`mchar`/`mvarchar`** — строки с семантикой MS SQL: **регистронезависимое** сравнение и сортировка, правила для концевых пробелов. Обычные B-tree индексы по таким колонкам работают без `lower()`. Модуль **`online_analyze`** сразу после заполнения таблицы (прежде всего **временной**) собирает по ней статистику — autovacuum до временных таблиц не доходит, без статистики планировщик ошибается в числе строк и выбирает плохой план. Рядом с ним используют **`plantuner`** (параметр `fix_empty_table`), который не даёт планировщику считать пустую на момент планирования временную таблицу «большой».

### `mchar` и `mvarchar`

- В стандартном PostgreSQL `varchar` сравнивается **с учётом регистра**, а обработка концевых пробелов отличается от MS SQL.
- База 1С на MS SQL создаётся с регистронезависимой коллацией (`Cyrillic_General_CI_AS`): `'Иванов' = 'иванов'`.
- `mchar`/`mvarchar` (расширение в сборке PostgreSQL для 1С) повторяют это поведение. Платформа хранит в них строковые реквизиты.
- Следствие для индексов: условие `ГДЕ Наименование = "иванов"` найдёт «Иванов» и **использует обычный индекс** по колонке. В стандартном PostgreSQL для регистронезависимого поиска понадобился бы индекс по выражению `lower(name)` или тип `citext`.

### `online_analyze`

**Проблема.** 1С активно использует временные таблицы (`ПОМЕСТИТЬ ВТ...`): создаются, заполняются и удаляются за доли секунды в одном сеансе. Autovacuum работает в фоне и **временные таблицы не обрабатывает вообще**. Без статистики планировщик предполагает число строк «наугад» → например, `Nested Loop` вместо `Hash Join` на сотнях тысяч строк → запрос выполняется минуты вместо секунд.

**Решение.** `online_analyze` выполняет `ANALYZE` **синхронно**, сразу после `INSERT/UPDATE/DELETE`/`SELECT INTO` в таблицу, если изменений достаточно.

```ini
# postgresql.conf — типичные значения из методических материалов 1С
shared_preload_libraries = 'online_analyze, plantuner'
online_analyze.enable = on
online_analyze.table_type = 'temporary'   # 'all' — для всех таблиц, но дороже
online_analyze.threshold = 50              # минимум изменённых строк
online_analyze.scale_factor = 0.1          # доля изменённых строк
online_analyze.min_interval = 10000        # мс между повторными анализами одной таблицы
online_analyze.verbose = off
plantuner.fix_empty_table = on
```

Цена — дополнительный CPU на каждое заполнение временной таблицы, но это несравнимо дешевле плохого плана.

### Что ещё важно

- `ИНДЕКСИРОВАТЬ ПО` во временной таблице на PostgreSQL создаёт реальный индекс — с ним и со свежей статистикой планировщик выбирает соединения правильно.
- Соединение с виртуальной таблицей `СрезПоследних` на PostgreSQL особенно часто даёт плохой план → выносить срез во временную таблицу.
- Настройки autovacuum для 1С обычно делают агрессивнее стандартных: таблицы итогов регистров обновляются очень часто ([3.5](03-postgresql.md)).

> **Запомнить:** `mvarchar`/`mchar` = строки «как в MS SQL» (регистронезависимо, обычный индекс работает). `online_analyze` = мгновенная статистика по временным таблицам. `plantuner.fix_empty_table` — защита от плохих планов на пустых таблицах.

## 5.4. Основные различия в организации индексов MS SQL и PostgreSQL, которые нужно учитывать в 1С

> **Коротко.** В MS SQL таблицы 1С — кластерные индексы, в PostgreSQL — кучи с вторичными индексами. В PostgreSQL `UPDATE` создаёт новую версию строки и часто правит все индексы (если нет HOT) → раздувание и обязательный VACUUM. Обслуживание разное: `REBUILD/REORGANIZE` + статистика против `VACUUM/ANALYZE` + `REINDEX CONCURRENTLY`. Строки — `nvarchar` с регистронезависимой коллацией против `mvarchar`. Статистика временных таблиц в PG — только через `online_analyze`. Набор индексов, который создаёт платформа, одинаков.

| Аспект | MS SQL Server | PostgreSQL |
|---|---|---|
| Таблица | Кластерный индекс (Ссылка, Период…) | Куча; тот же набор индексов — вторичные |
| Ссылка из индекса на строку | Ключ кластерного индекса | `ctid` (физический адрес) |
| `UPDATE` неиндексированной колонки | Только кластерный индекс (строка на месте) | Новая версия; без HOT — запись во **все** индексы |
| Мусор | Нет мёртвых версий в таблице (версии для snapshot — в tempdb) | Мёртвые версии в таблице и индексах до `VACUUM` |
| Обслуживание индексов | `REORGANIZE` / `REBUILD` (онлайн — Enterprise) | `VACUUM` (autovacuum), `REINDEX CONCURRENTLY`, `pg_repack` |
| Статистика | `UPDATE STATISTICS` / автообновление | `ANALYZE` / autovacuum; для временных таблиц — `online_analyze` |
| Fill factor | Только индексы, по умолчанию 100 | Таблицы (100, для HOT) и индексы (B-tree 90) |
| Строки | `nvarchar`, коллация `CI_AS` | `mvarchar`/`mchar` (сборка для 1С) |
| Типы индексов, которые создаёт платформа | B-tree | B-tree |
| Секционирование | Есть локальные и глобальные индексы | Только локальные |
| Мониторинг индексов | `sys.dm_db_index_usage_stats`, `sys.dm_db_missing_index_*` | `pg_stat_user_indexes`, `pg_stat_statements` |
| План запроса в ТЖ | Событие `DBMSSQL` + `<plansql/>` | Событие `DBPOSTGRS` + `<plansql/>` |

**Практические следствия при переходе с MS SQL на PostgreSQL:**
1. Настроить autovacuum и мониторинг раздувания — на MS SQL этой задачи не было.
2. Включить `online_analyze` и `plantuner`.
3. Перепроверить тяжёлые запросы: соединения с подзапросами и виртуальными таблицами (особенно `СрезПоследних`) планировщик PostgreSQL может обработать хуже — выносить во временные таблицы с индексами.
4. Переписать регламент обслуживания (см. [6.1](06-obsluzhivanie-diagnostika.md)).

## 5.5. Какие индексы и таблицы у регистра бухгалтерии и регистра расчёта

> **Коротко.** Регистр бухгалтерии хранится в нескольких таблицах. **Основная** (`_AccRgN`) — проводки: период, регистратор, номер строки, счёт (или счета Дт/Кт при корреспонденции), измерения, ресурсы. Индексы — как у движений регистра накопления: по **Периоду + Регистратору + НомеруСтроки** и по **Регистратору + НомеруСтроки**; для измерения с «Индексировать» — Измерение + Период + Регистратор + НомерСтроки. **Субконто** в основной таблице не лежат: каждое значение субконто — отдельная строка таблицы **значений субконто** (`_AccRgEDN`). **Итоги** — по счетам (`_AccRgAT0N`) и по счетам с первыми 1, 2, … N субконто (`_AccRgAT1N`, `_AccRgAT2N`…), обороты между счетами — `_AccRgCTN`. Отсюда два вывода для индексов: (1) **порядок видов субконто на счёте** работает как порядок измерений — отбор по Субконто2 без Субконто1 не использует левый префикс итогов; (2) **составной тип значений субконто** делает индексы таблиц субконто и итогов шире. У регистра расчёта есть основная таблица, таблица **периодов действия** (`_CRgActPN`) и таблица **перерасчётов** (`_CRgRecalcN`); тяжёлые запросы — к базе расчёта, где соединение идёт по **измерениям базы**.

> ℹ️ Состав таблиц — по описаниям структуры хранения 1С и книге «Реализация прикладных задач в системе 1С:Предприятие 8» (ИТС, глава о производительности регистра бухгалтерии). Точный состав индексов в своей базе проверяйте через `ПолучитьСтруктуруХраненияБазыДанных()`.

### Регистр бухгалтерии — таблицы

| Таблица | Что хранит | Индексы — главное |
|---|---|---|
| `_AccRgN` — основная | Проводки: Период, Регистратор, НомерСтроки, Счёт (или СчётДт/СчётКт), Активность, измерения (или Дт/Кт-пары при балансовых измерениях), ресурсы | По Периоду + Регистратору + НомеруСтроки; по Регистратору + НомеруСтроки; Измерение с «Индексировать» + Период + Регистратор + НомерСтроки |
| `_AccRgEDN` — значения субконто | Строка на **каждое** субконто каждой проводки: ссылка на проводку (Период, Регистратор, НомерСтроки), сторона Дт/Кт, **вид** субконто, **значение** | По проводке; по виду и значению субконто — для отборов «все проводки по контрагенту» |
| `_AccRgAT0N` | Итоги по счетам (без субконто) | Период + Счёт + измерения [+ Splitter] |
| `_AccRgAT1N`, `_AccRgAT2N`, … | Итоги по счетам **и** первым 1, 2, … субконто | Период + Счёт + Субконто1 [+ Субконто2 …] + измерения [+ Splitter] |
| `_AccRgCTN` | Обороты между счетами (корреспонденция) | Период + СчётДт + СчётКт + … |
| `_AccRgOptN` | Настройки хранения итогов | — |

### Что из этого следует

**1. Порядок видов субконто на счёте — тот же левый префикс.**
Итоги по второму субконто лежат в таблице, отсортированной по Счёту, **Субконто1**, Субконто2. Запрос «остатки по счёту 41 на складе» (Субконто2 = Склад) без отбора по Номенклатуре (Субконто1) не сможет использовать префикс индекса — придётся просмотреть все значения Субконто1 счёта. Поэтому при настройке плана счетов первым ставят субконто, по которому отбирают чаще. Изменить порядок в работающей базе = пересчёт итогов.

**2. Субконто — это соединение с отдельной таблицей.**
Виртуальная таблица `ДвиженияССубконто` и отборы по значению субконто в `Обороты`/`Остатки` по движениям — это соединение основной таблицы с `_AccRgED` (по одной на каждое нужное субконто). Отбор по значению субконто лучше передавать **в параметры виртуальной таблицы** — тогда он применяется к таблице субконто или итогов, а не к уже собранному результату.

**3. Составной тип значения субконто.**
Значения субконто берутся из плана видов характеристик; если там много типов, колонка значения хранится несколькими физическими колонками (`_TYPE`, `_RTRef`, `_RRRef`, `_N`, `_S`, …) — в таблице субконто и во **всех** таблицах итогов. Индексы становятся шире, лимит ключа расходуется быстрее ([2.1](02-mssql.md#21-каковы-ограничения-на-ключ-индекса-байты-число-колонок)). Минимизировать состав типов — та же рекомендация, что для реквизитов ([5.2](#52--какие-рекомендации-можно-дать-при-создании-индексов-объектов-метаданных-в-1с)).

**4. Количество субконто и признаки учёта.**
Чем больше максимальное количество субконто, тем больше таблиц итогов и тем дороже каждая проводка (запись итогов в несколько таблиц). Признак «Только обороты» у вида субконто убирает его из итогов-остатков.

### Регистр расчёта — таблицы

| Таблица | Что хранит | Зачем индексы |
|---|---|---|
| `_CRgN` — основная | Записи расчёта: регистратор, вид расчёта, период регистрации, период действия, базовый период, измерения, ресурсы | Индексы по регистратору и по периодам; по измерениям с «Индексировать» |
| `_CRgActPN` — периоды действия | Фактические периоды действия (если используется график) | Для виртуальной таблицы `ФактическийПериодДействия` |
| `_CRgRecalcN` — перерасчёты | Записи, требующие перерасчёта | По регистратору и измерениям |

Самый тяжёлый запрос регистра расчёта — **получение базы** (`БазаНачисления` и т.п.): соединение записей расчёта с записями базовых видов расчёта по **измерениям базы**. Если измерения базы не проиндексированы или идут не первыми, соединение превращается в сканирование. Отбор (по сотрудникам, по регистратору) — в параметры виртуальной таблицы.

> **Запомнить:** РБ = основная (проводки) + `ED` (значения субконто построчно) + `AT0…ATn` (итоги по счетам и первым N субконто) + `CT` (обороты между счетами). Порядок видов субконто = левый префикс итогов; составной тип субконто = широкие индексы. РР = основная + периоды действия + перерасчёты; узкое место — база по измерениям базы.

## 5.6. Как кластерный индекс по Ссылке (GUID) ведёт себя при вставке новых объектов

> **Коротко.** Ссылка 1С — 16-байтный идентификатор (`binary(16)` в MS SQL, `bytea` в PostgreSQL). Случайный GUID — худший ключ для кластерного индекса: каждая вставка попадает в случайное место дерева → «плохие» расщепления, фрагментация, низкая плотность страниц ([2.2](02-mssql.md#22--что-такое-fill-factor-и-зачем-может-потребоваться-его-менять-что-такое-page-split)). Платформа это учитывает: для ссылок объектов генерируются идентификаторы **на основе времени** (UUID версии 1), и при хранении байты переставлены так, что новые ссылки в среднем попадают в «правую» часть индекса. Строгого возрастания нет: идентификаторы выдаются пачками разным сеансам и процессам, поэтому вставки идут в несколько «точек роста». На практике фрагментация кластерных индексов справочников и документов растёт **умеренно**, а основной кандидат на «плохие» расщепления — индексы по Коду, Наименованию, строковым и ссылочным реквизитам.

> ℹ️ Устройство генерации ссылок не описано в официальной документации 1С; описание дано по разборам внешних авторов (см. [источники](08-istochniki.md)). Проверить на своей базе: выбрать последние созданные документы и посмотреть значения `_IDRRef` подряд.

### Почему для кластерного ключа важен порядок вставки

| Ключ | Куда попадает новая строка | Расщепления | Фрагментация |
|---|---|---|---|
| Возрастающий (`IDENTITY`, дата) | В конец индекса | «Хорошие» | Почти нет |
| Случайный GUID (`NEWID()`, UUID v4) | В случайную страницу | «Плохие», постоянно | Быстро растёт, плотность ~50–70% |
| GUID на основе времени с правильным порядком байт (`NEWSEQUENTIALID()`, UUID v7, ссылки 1С) | В конец своего «диапазона» | Преимущественно «хорошие» | Умеренная |

### Ссылки 1С

- **Объекты** (справочники, документы, ПВХ, …) получают ссылку, сгенерированную по времени. Случайные GUID (версии 4) используются для `Новый УникальныйИдентификатор()` и служебных идентификаторов.
- В базе ссылка хранится не в «строковом» порядке групп: части, задающие время, перенесены так, что сравнение байтов слева направо в основном совпадает с порядком создания внутри одного источника идентификаторов.
- Ссылки, присвоенные вручную (`УстановитьСсылкуНового()`, загрузка из другой базы по GUID), идут **в случайные места** индекса — массовая загрузка с сохранением ссылок фрагментирует кластерные индексы сильнее обычной работы.

### Что из этого следует для обслуживания

- Кластерный индекс по Ссылке — **не главный** источник фрагментации в типичной базе 1С.
- Индексы «Реквизит + Ссылка», «Наименование + Ссылка», «Код + Ссылка» — вставки в середину по первой колонке. Здесь фрагментация и расщепления заметнее; здесь и имеет смысл умеренный fill factor, если мониторинг показывает расщепления.
- Таблицы движений регистров начинаются с Периода — вставка в конец.
- Регистры сведений с кластерным индексом по измерениям-ссылкам — вставка в середину (первое измерение — ссылка на произвольный объект).

> **Запомнить:** случайный GUID в кластерном ключе = постоянные «плохие» split. Ссылки объектов 1С генерируются по времени и хранятся так, что в среднем растут → кластерный индекс по Ссылке фрагментируется умеренно. Сильнее страдают индексы «поле + Ссылка» и регистры сведений, а также базы после загрузки объектов с чужими GUID.

## 5.7. Как динамический список читает данные и какие индексы ему нужны

> **Коротко.** При включённом **динамическом считывании** список не читает таблицу целиком: он запрашивает **порцию** строк (`ПЕРВЫЕ N` / `TOP N`) в текущем порядке сортировки, а при прокрутке — следующую порцию с условием «после последней показанной строки». Чтобы порядок был однозначным, к пользовательской сортировке платформа добавляет **Ссылку**. Такой запрос быстрый, только если есть индекс, который **уже отсортирован** так же, как список, и начинается с полей отбора: тогда СУБД спускается по дереву и читает N строк подряд. Нет такого индекса → СУБД читает и сортирует всю отобранную выборку **на каждую порцию**. Отсюда «Индексировать с доп. упорядочиванием» (Реквизит + Наименование/Код/Дата + Ссылка) — ровно под список с отбором по реквизиту и стандартной сортировкой. Поиск по подстроке (`ПОДОБНО "%…%"`) индекс не использует.

### Как выглядит запрос порции

Упрощённо (MS SQL; точный текст виден в ТЖ):

```sql
-- первая порция: список документов с отбором по контрагенту, сортировка по дате
SELECT TOP 50 ...
FROM _Document123 T
WHERE T._Fld456RRef = @Контрагент
ORDER BY T._Date_Time, T._IDRRef;

-- следующая порция: «после последней строки»
SELECT TOP 50 ...
FROM _Document123 T
WHERE T._Fld456RRef = @Контрагент
  AND (T._Date_Time > @ПоследняяДата
       OR (T._Date_Time = @ПоследняяДата AND T._IDRRef > @ПоследняяСсылка))
ORDER BY T._Date_Time, T._IDRRef;
```

Идеальный индекс для этих запросов — `(_Fld456RRef, _Date_Time, _IDRRef)`: равенство по отбору первым, затем поля сортировки. Это и есть индекс «Контрагент + Дата + Ссылка», который платформа создаёт при **«Индексировать с доп. упорядочиванием»** у реквизита документа.

### Что сделает СУБД

| Есть индекс «Отбор + Сортировка + Ссылка» | Нет такого индекса |
|---|---|
| Спуск по дереву → чтение 50 строк подряд → готово | Найти **все** строки по отбору (или просканировать таблицу) → **отсортировать** → отдать первые 50 |
| Время не зависит от размера таблицы | Время растёт с размером выборки; повторяется на каждой прокрутке |

### Что ломает быстрый список

- **Сортировка по неиндексированному полю** (пользователь щёлкнул по колонке «Комментарий») или по полю через точку (`Контрагент.ИНН`).
- **Отбор по полю без индекса** или по нескольким полям, для которых нет общего индекса.
- **Поиск в списке** по подстроке — `ПОДОБНО "%текст%"` → сканирование. Помогает полнотекстовый поиск в списке (свой индекс 1С, не индекс СУБД) или поиск по началу строки.
- **Произвольный запрос** списка с соединениями, группировками, `РАЗЛИЧНЫЕ` — платформе сложнее построить порционное чтение, оптимизатору — найти индекс.
- **Ограничения доступа (RLS)** добавляют к каждой порции свои условия ([5.9](#59-как-ограничения-доступа-на-уровне-записей-rls-влияют-на-индексы-и-планы-запросов)).
- Отключённое динамическое считывание: список читает все строки.

### Рекомендации

1. Для частых отборов в списках — «Индексировать», а если список с отбором сортируется по коду, наименованию или дате — **«Индексировать с доп. упорядочиванием»**.
2. Ограничить в форме сортировку по колонкам без индекса или убрать такие колонки из сортируемых.
3. Основная таблица вместо произвольного запроса, где возможно; поля через точку — не в отборах и сортировке.
4. Для поиска по тексту — полнотекстовый поиск или поиск по началу строки.

> **Запомнить:** динамический список = `TOP N` + `ORDER BY` (сортировка + Ссылка) + условие «после последней строки». Быстро, если есть индекс «поля отбора + поля сортировки + Ссылка». «Индексировать с доп. упорядочиванием» создаёт именно его.

## 5.8. Что делает `ИНДЕКСИРОВАТЬ ПО` во временной таблице и когда это окупается

> **Коротко.** `ИНДЕКСИРОВАТЬ ПО Поле1, Поле2` в запросе с `ПОМЕСТИТЬ` заставляет платформу создать на временной таблице **реальный индекс СУБД** по этим полям (в указанном порядке — работает правило левого префикса). В MS SQL временная таблица — `#tt` в tempdb, без индекса это куча; с индексом — кластерный индекс по указанным полям. В PostgreSQL — таблица в схеме `pg_temp` и обычный B-tree. Индекс нужен, когда временная таблица **большая** (стандарт 1С: не индексировать таблицы до ~1000 записей) и участвует в **соединении** (поля из условия `ПО`) или в **`В (ВЫБРАТЬ …)`** (поля, соответствующие левой части `В`). Для маленьких таблиц построение индекса дороже выгоды.

### Как это выглядит

```bsl
ВЫБРАТЬ
    Т.Номенклатура, Т.Склад, СУММА(Т.Количество) КАК Количество
ПОМЕСТИТЬ ВТ_Товары
ИЗ Документ.РеализацияТоваровУслуг.Товары КАК Т
ГДЕ Т.Ссылка В (&Документы)
СГРУППИРОВАТЬ ПО Т.Номенклатура, Т.Склад
ИНДЕКСИРОВАТЬ ПО Номенклатура, Склад
;
ВЫБРАТЬ ...
ИЗ ВТ_Товары КАК ВТ
    ЛЕВОЕ СОЕДИНЕНИЕ РегистрНакопления.ТоварыНаСкладах.Остатки(
        , (Номенклатура, Склад) В (ВЫБРАТЬ Номенклатура, Склад ИЗ ВТ_Товары)) КАК Ост
    ПО ВТ.Номенклатура = Ост.Номенклатура И ВТ.Склад = Ост.Склад
```

В ТЖ на MS SQL видно создание `#tt` и затем создание индекса по указанным колонкам; на PostgreSQL — `CREATE TEMPORARY TABLE` и `CREATE INDEX` на `pg_temp.ttN`.

### Когда индекс нужен

| Ситуация | Индексировать по |
|---|---|
| Большая ВТ в соединении (с любой стороны) | Полям из условия `ПО` |
| ВТ в подзапросе `В (ВЫБРАТЬ …)` | Полям из списка выбора, соответствующим левой части `В` |
| Несколько условий, но часто проверяется одно | Этому полю (первым) |
| Маленькая ВТ (до ~1000 записей) | **Не индексировать** |

### Тонкости

- **Порядок полей** в `ИНДЕКСИРОВАТЬ ПО` важен: это составной индекс, первым — поле, по которому соединяют всегда.
- Поле **составного типа** в индексе — несколько физических колонок ([5.2](#52--какие-рекомендации-можно-дать-при-создании-индексов-объектов-метаданных-в-1с)).
- На **PostgreSQL** без статистики даже проиндексированная ВТ может получить плохой план — нужен `online_analyze` ([5.3](#53-какие-особенности-есть-у-1с-на-postgresql-mvarcharmchar-регистронезависимость-online_analyze)).
- Индекс не помогает, если временная таблица целиком читается в `Hash Join` — оптимизатору нужна только оценка числа строк. Индекс выигрывает в `Nested Loops` и `Merge Join`, где нужен поиск или порядок.
- Создание индекса — запись в tempdb: при очень частых запросах с ВТ это заметная нагрузка на tempdb.

> **Запомнить:** `ИНДЕКСИРОВАТЬ ПО` = реальный индекс СУБД на временной таблице (MS SQL — кластерный на `#tt`). Индексировать большие ВТ по полям соединения и `В (…)`; маленькие (< ~1000 строк) — нет. Порядок полей = левый префикс.

## 5.9. Как ограничения доступа на уровне записей (RLS) влияют на индексы и планы запросов

> **Коротко.** RLS — условие, которое платформа **добавляет к каждому запросу** к таблице с ограничением (в запросах `ВЫБРАТЬ РАЗРЕШЕННЫЕ`, в динамических списках, при чтении объектов). Для СУБД это дополнительные соединения или подзапросы `EXISTS`/`IN` к служебным таблицам прав и условия по полям ограничения (`Организация`, `Склад`, `Контрагент`). Последствия для индексов: (1) поля, по которым ограничивается доступ, становятся **частыми отборами** — их стоит индексировать или ставить первыми измерениями; (2) у пользователя с ограничениями **другой план**, чем у администратора, — проблему «тормозит только у бухгалтера» нужно воспроизводить под ним; (3) условия с `ИЛИ` и обращения через точку в шаблонах RLS ломают использование индексов. В БСП «производительный» вариант ограничения доступа строит условия через **ключи доступа** — короткие соединения по индексированным полям, поэтому он быстрее старого варианта на наборах значений.

### Что попадает в SQL

```bsl
// Текст ограничения роли (упрощённо, без БСП)
ГДЕ Организация В (&РазрешенныеОрганизации)
```

Платформа подставляет его во **все** запросы к таблице. Например, отчёт по остаткам регистра с ограничением по `Организации`:

- если `Организация` — **первое** измерение регистра (или проиндексирована), условие RLS работает как отбор по индексу;
- если `Организация` — третье измерение без индекса, ограничение превращается в фильтр после чтения → сканирование итогов на каждый запрос пользователя с ограничениями.

### БСП: два варианта

| | Стандартный (на наборах значений доступа) | Производительный (универсальное ограничение, ключи доступа) |
|---|---|---|
| Как строится условие | Шаблоны `#ПоЗначениям`, `#ПоНаборамЗначений`: подзапросы к регистрам значений и наборов доступа, часто с `ИЛИ` | Объекту при записи вычисляется **ключ доступа**; условие RLS — соединение с таблицей ключей пользователя |
| План | Сложные подзапросы, `ИЛИ`, ошибки оценки | Соединения по индексированным полям ключей |
| Цена | Дороже на чтении | Дороже на записи (обновление ключей), фоновое заполнение |

### Рекомендации

1. Поля, по которым настроено RLS, рассматривать как постоянные отборы: порядок измерений, «Индексировать».
2. Диагностику медленных запросов делать **под пользователем с ограничениями** (ТЖ с отбором по пользователю, ЦУП).
3. Не использовать в условиях ограничений обращения через точку к составным полям — неявные соединения со многими таблицами.
4. В БСП — по возможности производительный вариант ограничения доступа.

> **Запомнить:** RLS = добавочное условие в каждом запросе → поля ограничения работают как отборы и должны попадать в индексы. План у пользователя с ограничениями другой — диагностировать под ним.

## 5.10. Что такое разделение итогов и как оно влияет на индексы таблиц итогов

> **Коротко.** При записи движений регистра накопления (и бухгалтерии) платформа обновляет строки **таблицы итогов** с тем же периодом и теми же измерениями. Если много сеансов одновременно пишут движения по одной комбинации (например, продажи одного товара с одного склада в рознице), они **ждут друг друга** на блокировке одной строки итогов. **Разделение итогов** добавляет в таблицу итогов колонку **`Splitter`** — она входит **последним полем** в кластерный индекс итогов. Каждый сеанс пишет в «свою» строку с собственным значением разделителя, поэтому параллельная запись не конфликтует. Цена: строк итогов становится больше, при чтении остатков их нужно суммировать. Подходит, когда при записи **нет чтения** этого регистра (контроля остатков) в той же транзакции.

### Как это устроено

```
Без разделения:  Период | Склад | Номенклатура            → одна строка на комбинацию
С разделением:   Период | Склад | Номенклатура | Splitter → несколько строк, по одной на сеанс-«писатель»
```

| | Без разделения | С разделением |
|---|---|---|
| Ключ кластерного индекса итогов | Период + Измерения | Период + Измерения + **Splitter** |
| Параллельная запись по одной комбинации | Сеансы ждут друг друга (блокировка строки итогов) | Пишут в разные строки, не ждут |
| Чтение остатков | Одна строка на комбинацию | Сумма нескольких строк (`GROUP BY` без Splitter) — немного дороже |
| Размер таблицы итогов | Меньше | Больше |

Свойство регистра — «Разрешить разделение итогов»; управление в коде — `УстановитьИспользованиеРазделенияИтогов()`. Наличие `Splitter` в индексе видно в `ПолучитьСтруктуруХраненияБазыДанных()` и в среде СУБД.

### Когда включать

- **Да:** много одновременных записей по одним и тем же измерениям **без** контроля остатков при записи (розничные продажи, массовая регистрация событий).
- **Нет / бесполезно:** при записи в той же транзакции читаются остатки этого регистра (контроль остатков). Чтение требует согласованных итогов, параллельности не получится.
- Разделение итогов решает конфликт **записи в итоги**, а не медленные запросы: на чтение оно влияет в худшую сторону, хоть и немного.

### Связь с индексами

- `Splitter` в конце ключа не мешает отборам по измерениям: левый префикс «Период + Измерения» сохраняется.
- Таблица итогов растёт → больше страниц → больше работы при сканировании итогов.
- Аналог из мира СУБД — идея индексированных представлений и агрегатов: заранее посчитанный результат, который дорого поддерживать при параллельной записи ([2.8](02-mssql.md#28-как-в-ms-sql-проиндексировать-выражение-вычисляемые-столбцы-и-индексированные-представления)).

> **Запомнить:** Splitter = последнее поле кластерного индекса итогов; у каждого сеанса своя строка итогов → нет ожиданий при параллельной записи. Цена — больше строк итогов и суммирование при чтении. Не помогает при контроле остатков.
