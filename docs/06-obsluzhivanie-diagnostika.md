## 6.1. Каков регламент обслуживания индексов и статистики для баз 1С на MS SQL и на PostgreSQL

> **Коротко.** **MS SQL:** ежедневно — обновление статистики (`UPDATE STATISTICS`, после массовых загрузок — внепланово) и затем очистка процедурного кэша; обслуживание индексов (`REORGANIZE`/`REBUILD`) — в технологическое окно, **выборочно** по крупным индексам с измеренной фрагментацией или низкой плотностью; плюс проверка целостности и бэкапы. **PostgreSQL:** основную работу делает **autovacuum** (очистка мёртвых версий + `ANALYZE`) — его нужно настроить агрессивнее стандартного и следить за долгими транзакциями; статистика временных таблиц — `online_analyze`; при раздувании индексов — `REINDEX CONCURRENTLY` или `pg_repack` по расписанию (раз в неделю/месяц по факту). Реиндексация через «Тестирование и исправление» в конфигураторе требует монопольного режима — для регулярного обслуживания используют средства СУБД.

### MS SQL Server

| Операция | Зачем | Когда |
|---|---|---|
| **Обновление статистики** | Оптимизатор строит планы по актуальному распределению данных | **Ежедневно** + сразу после массовых загрузок, закрытия месяца, свёртки |
| **Очистка процедурного кэша** (`DBCC FREEPROCCACHE`) | Сбросить планы, построенные по старой статистике | Сразу после обновления статистики (рекомендация методики 1С) |
| **Дефрагментация индексов** | Уплотнить страницы, восстановить порядок | В технологическое окно; классически — ежедневно, современный подход — **выборочно** по измерению |
| Проверка целостности (`DBCC CHECKDB`) | Найти повреждения | Регулярно (например, еженедельно) |
| Резервное копирование | — | По политике |

**Обновление статистики:**
```sql
EXEC sp_updatestats;                          -- только там, где были изменения, с выборкой
-- или для конкретной большой таблицы:
UPDATE STATISTICS dbo._AccumRgT1234 WITH FULLSCAN;
-- затем
DBCC FREEPROCCACHE;
```
`sp_updatestats` проходит по всем таблицам, но обновляет только статистику, где были изменения. Полное `WITH FULLSCAN` по всей базе точнее, но на больших базах может не уложиться в окно.

> ⚠️ **Нюанс про `DBCC FREEPROCCACHE`.** Очистку кэша после обновления статистики рекомендует методика 1С — на аттестации её нужно называть. Но знайте, что обновлённая статистика **сама** помечает зависимые планы для перекомпиляции при следующем выполнении. Полная очистка кэша сбрасывает **все** планы экземпляра (всех баз на сервере), и следующие минуты сервер тратит CPU на компиляцию. Аккуратнее — очищать кэш только своей базы: `ALTER DATABASE SCOPED CONFIGURATION CLEAR PROCEDURE_CACHE;` (SQL Server 2016+, выполняется в контексте базы).

**Индексы — выборочно:**
```sql
-- REORGANIZE для умеренной фрагментации, REBUILD для сильной, маленькие пропускаем
ALTER INDEX [имя] ON [таблица] REORGANIZE;
ALTER INDEX [имя] ON [таблица] REBUILD WITH (ONLINE = ON, SORT_IN_TEMPDB = ON); -- ONLINE: Enterprise
```
Отраслевой стандарт для этого — процедура `IndexOptimize` из скриптов Ola Hallengren.

> ⚠️ **Поправка к ответу NotebookLM:** `sp_msforeachtable 'DBCC DBREINDEX(''?'')'` — устаревший способ: `DBCC DBREINDEX` объявлен устаревшим, а `sp_msforeachtable` — недокументированная процедура. Используйте `ALTER INDEX ... REBUILD/REORGANIZE` и выборочный подход.

**Настройки базы, связанные со статистикой:**
- `AUTO_CREATE_STATISTICS = ON`, `AUTO_UPDATE_STATISTICS = ON` — оставить включёнными;
- `AUTO_UPDATE_STATISTICS_ASYNC` — `ON` при ровной OLTP-нагрузке (запрос не ждёт пересчёта статистики), `OFF`, если бывают резкие изменения объёма данных (загрузки), — чтобы запрос сразу получил свежую статистику.

### PostgreSQL

| Операция | Зачем | Когда |
|---|---|---|
| **Autovacuum** (`VACUUM` + `ANALYZE`) | Удалить мёртвые версии из таблиц и индексов, обновить карту видимости и статистику | Постоянно, автоматически. Настроить пороги и число рабочих процессов |
| Ручной `VACUUM ANALYZE` | Помочь autovacuum на самых нагруженных таблицах | По расписанию в часы низкой нагрузки (ночью) |
| **`online_analyze`** | Статистика временных таблиц 1С | Постоянно включён |
| Контроль долгих транзакций | Не дать «горизонту» остановить очистку | Мониторинг `pg_stat_activity`, `idle_in_transaction_session_timeout` |
| **`REINDEX CONCURRENTLY`** / **`pg_repack`** | Убрать раздувание индексов и таблиц | Раз в неделю/месяц, по результатам мониторинга раздувания |
| `VACUUM FULL` | Сжать таблицу | Только в окно простоя (полная блокировка) |

Типичная настройка autovacuum для базы 1С (ориентир, подбирается под нагрузку):
```ini
autovacuum = on
autovacuum_max_workers = 4               # больше рабочих — больше таблиц обрабатывается параллельно
autovacuum_naptime = 20s
autovacuum_vacuum_scale_factor = 0.01    # вместо 0.2 — чистить раньше на больших таблицах
autovacuum_analyze_scale_factor = 0.005  # вместо 0.1
autovacuum_vacuum_cost_limit = 2000      # дать autovacuum работать быстрее
maintenance_work_mem = 1GB               # меньше повторных проходов по индексам
```

## 6.2. Как найти медленный запрос и связанный с ним индекс: технологический журнал, ЦУП, Profiler / Extended Events, `pg_stat_statements`

> **Коротко.** Задача из двух шагов: **поймать** медленный запрос (текст + длительность + место в коде 1С) и **прочитать его план**, где видно, какой индекс используется (`Index Seek`, `Index Scan`) или не нашёлся (`Table Scan`, `Seq Scan`). Инструменты: **технологический журнал 1С** — события `DBMSSQL`/`DBPOSTGRS` с отбором по длительности, `<plansql/>` для плана, контекст кода; **1С:ЦУП** — то же автоматически, с ранжированием и физическими именами → метаданные; **Profiler / Extended Events** (MS SQL) — события завершения запросов + `showplan`; **`pg_stat_statements` + лог медленных запросов + `EXPLAIN (ANALYZE, BUFFERS)`** (PG). Физические имена таблиц и индексов переводятся в метаданные через `ПолучитьСтруктуруХраненияБазыДанных()`.

```mermaid
flowchart LR
    S["Жалоба:<br/>«тормозит отчёт»"] --> capture
    subgraph capture["Шаг 1: поймать запрос"]
        T1["ТЖ 1С<br/>DBMSSQL / DBPOSTGRS<br/>+ контекст"]
        T2["ЦУП"]
        T3["MS SQL:<br/>Extended Events / Profiler"]
        T4["PG:<br/>pg_stat_statements,<br/>log_min_duration_statement"]
    end
    capture --> P["Шаг 2: план запроса<br/>&lt;plansql/&gt;, showplan,<br/>EXPLAIN (ANALYZE, BUFFERS)"]
    P --> M["Шаг 3: физические имена → метаданные<br/>ПолучитьСтруктуруХраненияБазыДанных()"]
    M --> F["Шаг 4: решение:<br/>метаданные / текст запроса / статистика"]
```

### 1. Технологический журнал 1С

Работает с любой СУБД и сразу связывает SQL с кодом 1С. Пример `logcfg.xml`:

```xml
<config xmlns="http://v8.1c.ru/v8/tech-log">
  <log location="C:\v8logs\slow_sql" history="24">
    <event>
      <eq property="name" value="DBMSSQL"/>      <!-- MS SQL -->
      <ge property="duration" value="1000000"/> <!-- 8.3: микросекунды, т.е. > 1 с -->
    </event>
    <event>
      <eq property="name" value="DBPOSTGRS"/>    <!-- PostgreSQL -->
      <ge property="duration" value="1000000"/>
    </event>
    <property name="all"/>
  </log>
  <plansql/>                                   <!-- писать план запроса -->
</config>
```

- В событии: `duration` — длительность, `Sql` — текст запроса в терминах СУБД, `Context` — модуль и строка кода 1С, `planSQLText` — план (если включён `<plansql/>`).
- В плане ищем операторы и **имена индексов**: `Clustered Index Seek(OBJECT:([base].[dbo].[_AccumRgT1234].[_AccumRgT1234_ByPeriod...]))` или `Index Scan using _accumrgt1234_... on _accumrgt1234`.
- ⚠️ Сбор планов создаёт заметную нагрузку — включать на ограниченное время и с отбором по длительности.

### 2. 1С:ЦУП (Центр управления производительностью)

- Сам собирает данные ТЖ/СУБД, **ранжирует проблемы по суммарному времени** («вес»), группирует по контексту и по таблицам.
- По запросу показывает: **контекст** (строка кода), **текст** запроса, **план** с подсветкой проблемных операторов.
- Сопоставление физических имён с метаданными — автоматически.

### 3. MS SQL Server: Extended Events и Profiler

**Extended Events** — современный и лёгкий инструмент (Profiler объявлен устаревшим и сильно нагружает сервер):

```sql
CREATE EVENT SESSION slow_queries ON SERVER
ADD EVENT sqlserver.rpc_completed (
    ACTION (sqlserver.sql_text, sqlserver.database_name, sqlserver.plan_handle)
    WHERE duration > 1000000),                    -- микросекунды: > 1 c
ADD EVENT sqlserver.sql_batch_completed (
    ACTION (sqlserver.sql_text, sqlserver.database_name, sqlserver.plan_handle)
    WHERE duration > 1000000)
ADD TARGET package0.event_file (SET filename = N'slow_queries.xel');
ALTER EVENT SESSION slow_queries ON SERVER STATE = START;
```

- План — событие `query_post_execution_showplan` (дорогое) или по `plan_handle` из `sys.dm_exec_query_stats` + `sys.dm_exec_query_plan`.
- **Query Store** (SQL Server 2016+) хранит историю запросов, их статистику и планы — удобно видеть, когда план «испортился».
- **Profiler:** события `RPC:Completed`, `SQL:BatchCompleted` (колонки `Duration`, `CPU`, `Reads`) и `Showplan XML Statistics Profile`; сортируем по `Duration`, план — в событии рядом.
- Без трассировки — топ запросов из кэша планов: `sys.dm_exec_query_stats` + `sys.dm_exec_sql_text` + `sys.dm_exec_query_plan`.

### 4. PostgreSQL

- `pg_stat_statements` — топ по `total_exec_time`, `mean_exec_time`, `shared_blks_read` ([3.7](03-postgresql.md)).
- `log_min_duration_statement = 1000` — медленные запросы в лог; `auto_explain` — с планами.
- `EXPLAIN (ANALYZE, BUFFERS)` над найденным запросом:
  - `Seq Scan on _accumrgt1234` — индекс не используется;
  - `Index Scan using <индекс> on <таблица>` — поиск по индексу с обращением к таблице;
  - `Index Only Scan using <индекс>` — только индекс;
  - `Bitmap Index Scan on <индекс>` — битовая карта.

> ⚠️ Запросы 1С на PostgreSQL часто используют временные таблицы (`pg_temp.tt1`), которые исчезают после выполнения. Чтобы повторить такой запрос через `EXPLAIN`, нужно воспроизвести и шаги, создающие временные таблицы.

### 5. Физическое имя → объект 1С

`ПолучитьСтруктуруХраненияБазыДанных()` — см. [5.1](05-1c.md#как-узнать-физические-имена-таблиц-и-индексов). В ЦУП — автоматически.

> **Запомнить:** поймать (ТЖ / ЦУП / XE / pg_stat_statements) → посмотреть план (`<plansql/>` / showplan / `EXPLAIN ANALYZE`) → перевести имена в метаданные (`ПолучитьСтруктуруХраненияБазыДанных`).

## 6.3. Кейс: отчёт по регистру тормозит. Порядок диагностики и варианты решения через индексы

> **Коротко.** **Диагностика:** (1) понять, где время — в СУБД или в коде 1С (замер производительности, ТЖ); (2) найти тяжёлый запрос и его план (ТЖ с `<plansql/>`, ЦУП, XE, `EXPLAIN ANALYZE`); (3) в плане смотреть сканирования больших таблиц, `Key Lookup`, расхождение оценки и факта строк; (4) проверить текст запроса: отборы в параметрах виртуальной таблицы, соединения с подзапросами, обращения через точку. **Решения:** перенести отбор в параметры виртуальной таблицы; изменить порядок измерений или поставить «Индексировать» у отбираемого измерения (у регистра сведений индекс даёт и «Ведущее»); вынести данные во временную таблицу с `ИНДЕКСИРОВАТЬ ПО`; включить агрегаты / проверить актуальность итогов; обновить статистику (и `online_analyze` на PG); только затем — обслуживание индексов.

```mermaid
flowchart TB
    A["Отчёт по регистру работает медленно"] --> B{"Где тратится время?<br/>Замер производительности, ТЖ"}
    B -->|"код 1С: циклы,<br/>запросы в цикле, вывод"| B1["Исправлять алгоритм,<br/>не индексы"]
    B -->|"СУБД: долгий запрос"| C["Найти запрос и план<br/>ТЖ + plansql / ЦУП / XE / EXPLAIN ANALYZE"]
    C --> D{"Что в плане?"}
    D -->|"Scan большой таблицы<br/>итогов или движений"| E{"Есть ли отбор<br/>по ведущим измерениям?"}
    E -->|"отбор в ГДЕ,<br/>а не в параметрах ВТ"| E1["Перенести отбор<br/>в параметры виртуальной таблицы"]

    D -->|"чтение движений<br/>за годы"| I["Агрегаты (обороты),<br/>актуальные итоги, разделение итогов"]
    E1 & E2 & F & G & H & I --> J["Повторный замер;<br/>обслуживание индексов — если нужно"]
```

### Шаг 1. Где тратится время

- **Замер производительности** в отладчике: время на строках кода. Если медленно не запрос, а обработка результата, вывод в табличный документ, запросы в цикле — индексы не помогут.
- **ТЖ** (`DBMSSQL`/`DBPOSTGRS` + `Context`): длительность каждого SQL-запроса отчёта.

### Шаг 2. План запроса

| Что видим в плане | Что это значит |
|---|---|
| `Clustered Index Scan` / `Table Scan` / `Seq Scan` по `_AccumRgT…` или `_AccumRg…` | Таблица читается целиком: нет подходящего индекса или отбор не доходит до таблицы |
| `Index Seek` + тысячи `Key Lookup` | Индекс находит строки, но не содержит нужных полей |
| Оценка 1 строка — факт 300 000 | Статистика устарела или её нет (временная таблица в PG без `online_analyze`) |
| `Nested Loops` с большим числом повторов внутренней части | Ошибка оценки или соединение с подзапросом |
| `Sort` / `Hash` со сбросом в tempdb / на диск | Не хватило памяти; часто — следствие той же ошибки оценки |

### Шаг 3. Текст запроса

- Отбор в **параметрах виртуальной таблицы**: `РегистрНакопления.ТоварыНаСкладах.Остатки(&Дата, Склад = &Склад)`, а не `... .Остатки(&Дата) ГДЕ Склад = &Склад`. Так условие попадает в запрос к таблице итогов и использует её индекс.
- **Соединения** с виртуальными таблицами и подзапросами → выносить во временные таблицы. Особенно на PostgreSQL и особенно `СрезПоследних`.
- Обращения **через точку** к составным полям (`Регистратор.Дата`) → `ВЫРАЗИТЬ` или денормализация.

### Варианты решения

| № | Решение | Когда помогает |
|---|---|---|
| 1 | **Отбор — в параметры виртуальной таблицы** | Отбор в `ГДЕ` по измерениям регистра |
| 2 | **Порядок измерений**: отбираемое измерение — первым | Отбор по измерению, которое стоит не первым, а отборы по нему основные |
| 3 | **«Индексировать»** у измерения (у регистра сведений индекс создаётся и для «Ведущего»; у регистров накопления и бухгалтерии свойства «Ведущее» нет) | То же, но порядок менять нельзя или отборы бывают по разным измерениям |
| 4 | **Без «дыр»** в отборе: измерения, по которым отбирают вместе, — подряд | Отбор по 1-му и 3-му измерениям |
| 5 | **Временная таблица + `ИНДЕКСИРОВАТЬ ПО`** | Соединение с большим подзапросом / виртуальной таблицей |
| 6 | **Агрегаты** (регистр оборотов), **актуальные итоги**, разделение итогов | Обороты за длинные периоды; старый период рассчитанных итогов (остатки считаются от далёкой даты по движениям) |
| 7 | **Статистика**: `UPDATE STATISTICS` / `ANALYZE`, на PG — `online_analyze` | Оценка строк сильно не совпадает с фактом |
| 8 | **Обслуживание индексов** | Подтверждённое раздувание / фрагментация больших индексов |

> 💡 Проверьте период рассчитанных итогов (`ПолучитьПериодРассчитанныхИтогов()`): если итоги рассчитаны давно, остатки на текущую дату платформа досчитывает по таблице движений за весь промежуток — отчёт медленный при любом индексе.

> **Запомнить:** сначала измерить, где время; потом план; потом текст запроса. Индексные решения в 1С — через параметры виртуальных таблиц, порядок измерений, «Индексировать», временные таблицы с индексами, статистику.

## 6.4. Как найти дублирующиеся и пересекающиеся индексы

> **Коротко.** **Дубликат** — два индекса с одинаковыми ключевыми колонками в одном порядке. **Пересекающийся (избыточный)** — индекс, ключ которого является **левым префиксом** другого: `(A)` при наличии `(A, B)`. Почти любой запрос, которому подходит `(A)`, может использовать `(A, B)`, а запись платит за оба. Но удалять «короткий» индекс можно не всегда: он может обеспечивать **уникальность**, быть **фильтруемым/частичным**, иметь другие `INCLUDE`, другое направление сортировки, быть заметно **меньше** (для частых сканирований это важно), быть кластерным. Ищут через системные представления (`sys.index_columns` в MS SQL, `pg_index.indkey` в PostgreSQL), решение принимают вручную и по статистике использования. В 1С индексы создаёт платформа: пересечения её индексов убирают свойствами метаданных в конфигураторе, а «ручные» индексы в базе — удаляют.

### Виды

| Вид | Пример | Можно удалить? |
|---|---|---|
| Точный дубликат | `IX1 (A, B)` и `IX2 (A, B)` | Да, один из двух (если оба неуникальные и без фильтра) |
| Левый префикс | `IX1 (A)` и `IX2 (A, B)` | Обычно да — `IX1` |
| Перестановка | `(A, B)` и `(B, A)` | **Нет** — разные префиксы, разные запросы |
| Отличаются `INCLUDE` | `(A) INCLUDE (C)` и `(A, B)` | Объединить: `(A, B) INCLUDE (C)` |

### Когда «лишний» индекс не лишний

- **Уникальный:** `UNIQUE (A)` нельзя заменить индексом `(A, B)` — это другое правило.
- **Фильтруемый / частичный:** `(A) WHERE Status = 1` может быть в десятки раз меньше.
- **Размер:** `(A)` при широком `(A, B, C, D)` в разы компактнее — для сканирований по `A` выгоднее.
- **Кластерный** индекс и индекс под внешний ключ.
- **Разная сортировка:** `(A ASC, B DESC)` и `(A, B)` обслуживают разные `ORDER BY`.

### MS SQL: поиск по ключевым колонкам

```sql
WITH k AS (
    SELECT ic.object_id, ic.index_id,
           STRING_AGG(CAST(ic.column_id AS varchar(10)), ',')
               WITHIN GROUP (ORDER BY ic.key_ordinal) AS cols      -- SQL Server 2017+
    FROM sys.index_columns AS ic
    WHERE ic.is_included_column = 0
    GROUP BY ic.object_id, ic.index_id
)
SELECT OBJECT_NAME(a.object_id) AS table_name,
       ia.name AS redundant_index, a.cols AS redundant_cols,
       ib.name AS covered_by,      b.cols AS covering_cols
FROM k AS a
JOIN k AS b  ON b.object_id = a.object_id AND b.index_id <> a.index_id
            AND b.cols + ',' LIKE a.cols + ',%'                       -- a — левый префикс b (или дубль)
JOIN sys.indexes AS ia ON ia.object_id = a.object_id AND ia.index_id = a.index_id
JOIN sys.indexes AS ib ON ib.object_id = b.object_id AND ib.index_id = b.index_id
WHERE OBJECTPROPERTY(a.object_id, 'IsUserTable') = 1
  AND ia.is_unique = 0 AND ia.has_filter = 0 AND ia.type_desc = 'NONCLUSTERED'
ORDER BY table_name, redundant_index;
```

Запрос сравнивает только ключевые колонки и их порядок; направление сортировки и `INCLUDE` проверить глазами.

### PostgreSQL: поиск по `pg_index.indkey`

```sql
SELECT a.indrelid::regclass   AS table_name,
       a.indexrelid::regclass AS redundant_index,
       b.indexrelid::regclass AS covered_by,
       pg_size_pretty(pg_relation_size(a.indexrelid)) AS redundant_size
FROM pg_index AS a
JOIN pg_index AS b  ON b.indrelid = a.indrelid AND b.indexrelid <> a.indexrelid
JOIN pg_class AS ca ON ca.oid = a.indexrelid
JOIN pg_class AS cb ON cb.oid = b.indexrelid
WHERE ca.relam = cb.relam                                   -- одинаковый тип индекса (B-tree с B-tree)
  AND (b.indkey::text || ' ') LIKE (a.indkey::text || ' %') -- a — левый префикс b (или дубль)
  AND NOT a.indisunique
  AND a.indpred IS NULL AND a.indexprs IS NULL              -- не частичный, не по выражению
  AND b.indpred IS NULL AND b.indexprs IS NULL              -- «покрывающий» тоже полный
ORDER BY pg_relation_size(a.indexrelid) DESC;
```

`indkey` в PostgreSQL 11+ содержит и `INCLUDE`-колонки (первые `indnkeyatts` — ключевые) — результат тоже проверять вручную.

### Порядок действий

1. Найти кандидатов запросом.
2. Проверить по статистике использования за полный бизнес-цикл ([2.4](02-mssql.md#24-что-показывают-sysdm_db_index_usage_stats-и-sysdm_db_missing_index_-ограничения-рекомендаций-по-недостающим-индексам), [3.7](03-postgresql.md#37-как-найти-неиспользуемые-индексы-и-проблемные-запросы-pg_stat_user_indexes-explain-analyze-pg_stat_statements)), что «короткий» индекс не выигрывает у «длинного».
3. В MS SQL — сначала `ALTER INDEX ... DISABLE` (определение остаётся, вернуть — `REBUILD`), понаблюдать, затем удалить. В PostgreSQL — `DROP INDEX CONCURRENTLY`.

### Применительно к 1С

Удалять индексы платформы средствами СУБД нельзя: при следующей реструктуризации они вернутся, а до неё возможны ошибки. Поэтому в базе 1С поиск дублей нужен для двух вещей:

| Что находим | Пример | Что делать |
|---|---|---|
| Пересечение индексов **платформы** | Реквизит входит в критерий отбора (индекс «Реквизит») и проиндексирован (индекс «Реквизит + Ссылка») — первый является префиксом второго | Решать в конфигураторе: нужны ли оба признака |
| Индексы, созданные **вручную** администраторами (например, по рекомендациям missing index) | Ручной `IX_…(_Fld123RRef)` при платформенном «Реквизит + Ссылка» | Удалить ручной индекс, задачу решить свойствами метаданных |

Имена индексов платформы начинаются с имени таблицы (`_Document123_ByField456_RR`…) — так ручные индексы легко отличить.

> **Запомнить:** дубль — одинаковые ключи; избыточный — левый префикс другого. Не удалять уникальные, фильтруемые, заметно меньшие, с другой сортировкой. Искать по `sys.index_columns` / `pg_index.indkey`, решать по статистике использования. В 1С — решать свойствами метаданных, ручные индексы в базе удалять.

## 6.5. Как статистика влияет на выбор индекса: пороги обновления, возрастающий ключ, коррелированные условия

> **Коротко.** Seek или Scan, Key Lookup или нет, `Nested Loops` или `Hash Join` — оптимизатор выбирает по **оценке числа строк**, а её берёт из статистики ([1.3](01-teoriya.md#13-что-такое-селективность-и-кардинальность)). В базах 1С три типовые ловушки. **1) Порог обновления.** MS SQL обновляет статистику автоматически, когда изменилось 500 + 20% строк; с уровня совместимости 130 (SQL Server 2016) порог динамический — не больше √(1000·n). PostgreSQL запускает `ANALYZE` после изменения 50 + 10% строк. На больших таблицах это долго. **2) Возрастающий ключ.** Новые строки с `Период`/`Дата` после последнего обновления статистики лежат за пределами гистограммы: старая модель оценки MS SQL считает, что там 1 строка, PostgreSQL тоже сильно занижает. Итог — `Nested Loops` + Lookup на сотни тысяч строк, «утром быстро, к вечеру медленно». **3) Коррелированные условия** (Организация + Склад): оптимизатор считает условия независимыми и перемножает их селективности → недооценка. В PostgreSQL лечится расширенной статистикой `CREATE STATISTICS`, в MS SQL частично помогают многоколоночная статистика (вектор плотности) и новая модель оценки.

### Что хранится в статистике — подробнее, чем в 1.3

**MS SQL Server.** Объект статистики создаётся на каждый индекс (по его ключевым колонкам) и автоматически на отдельные колонки из условий запросов (`_WA_Sys_…`). В нём три части:
- **заголовок** — когда обновлена, сколько строк было и сколько прочитано в выборке;
- **вектор плотности** — для каждого левого префикса ключа (`A`, `A+B`, `A+B+C`) плотность = 1 / число различных значений;
- **гистограмма** — до 200 шагов, **только по первой колонке**: верхняя граница шага (`RANGE_HI_KEY`), строк, равных границе (`EQ_ROWS`), строк внутри шага (`RANGE_ROWS`), различных значений внутри шага.

**PostgreSQL.** Статистика ведётся по колонкам (`pg_stats`): частые значения (MCV), гистограмма, `n_distinct`, `correlation`. `ANALYZE` читает выборку из 300 × `default_statistics_target` строк (по умолчанию 30 000). Многоколоночной статистики по индексу **нет**: индекс `(org, sklad)` не даёт планировщику знания о парах значений. Отдельная статистика собирается только для **выражений** в индексах по выражению ([3.9](03-postgresql.md#39-что-такое-индекс-по-выражению-в-postgresql-и-когда-он-нужен)).

### Когда статистика обновляется

| | MS SQL Server | PostgreSQL |
|---|---|---|
| Автоматически | При компиляции запроса, если счётчик изменений превысил порог | `ANALYZE` от autovacuum, если изменений больше порога |
| Порог | До уровня совместимости 130: 500 + 20% строк. С 130: меньшее из 500 + 20% и √(1000·n) | `autovacuum_analyze_threshold` + `autovacuum_analyze_scale_factor` × строк = 50 + 10% |
| Пример: 1 млн строк | 200 500 → **31 623** | ~100 050 |
| Пример: 100 млн строк | 20 000 500 → **316 228** | ~10 000 050 |
| Настройка для таблицы | Задание с `UPDATE STATISTICS` чаще общего регламента | `ALTER TABLE … SET (autovacuum_analyze_scale_factor = 0.01)` |
| Временные таблицы | Автоматически, как обычные (у маленьких `#tt` пороги ниже: 6 и 500 изменений) | **Никогда** — только `ANALYZE` вручную или `online_analyze` ([5.3](05-1c.md#53-какие-особенности-есть-у-1с-на-postgresql-mvarcharmchar-регистронезависимость-online_analyze)) |
| Перестроение индекса | `REBUILD` обновляет статистику этого индекса с полным сканированием | `REINDEX` статистику **не** обновляет |
| Ловушка | Автообновление берёт выборку по умолчанию и может затереть ночной `FULLSCAN`. Против этого — `PERSIST_SAMPLE_PERCENT = ON` (SQL Server 2016 SP1 CU4 / 2017 CU1+) | Долгие транзакции и отставший autovacuum откладывают и `ANALYZE` |

Как посмотреть свежесть статистики:

```sql
-- MS SQL: когда обновлена и сколько изменений накопилось
SELECT OBJECT_NAME(s.object_id) AS table_name, s.name AS stats_name,
       sp.last_updated, sp.rows, sp.rows_sampled, sp.modification_counter,
       CAST(100.0 * sp.modification_counter / NULLIF(sp.rows, 0) AS decimal(9,2)) AS mod_pct
FROM sys.stats AS s
CROSS APPLY sys.dm_db_stats_properties(s.object_id, s.stats_id) AS sp
WHERE OBJECTPROPERTY(s.object_id, 'IsUserTable') = 1
ORDER BY sp.modification_counter DESC;

-- Гистограмма конкретной статистики
DBCC SHOW_STATISTICS (N'dbo._AccumRg1234', N'<имя индекса или статистики>') WITH HISTOGRAM;
```

```sql
-- PostgreSQL: когда был ANALYZE и сколько изменений с тех пор
SELECT relname, last_analyze, last_autoanalyze, n_mod_since_analyze, n_live_tup
FROM pg_stat_user_tables
ORDER BY n_mod_since_analyze DESC;
```

### Проблема возрастающего ключа

Колонка, значения которой всегда растут (дата, период, номер), — худший случай для статистики: все **новые** строки лежат правее последнего шага гистограммы, а гистограмма о них не знает.

- **MS SQL, старая модель оценки** (уровень совместимости ≤ 110 или `LEGACY_CARDINALITY_ESTIMATION = ON`): значение за последней границей гистограммы → оценка **1 строка**. Для старой модели есть флаги трассировки 2389/2390 — «быстрая» статистика для возрастающих колонок.
- **MS SQL, новая модель** (SQL Server 2014+, уровень совместимости 120+): предполагает, что за пределами гистограммы строки есть, и оценивает их по плотности и числу изменений с последнего обновления. Ошибка меньше, но не исчезает.
- **PostgreSQL:** если по колонке есть B-tree индекс, планировщик заглядывает в него за реальным минимумом/максимумом, но расширяет им только **крайний интервал** гистограммы, который «весит» около 1% выборки. В скрипте [sql/postgresql/08_statistics_plans.sql](../sql/postgresql/08_statistics_plans.sql): 50 000 строк после последнего `ANALYZE` → оценка **32 строки**; после `ANALYZE` — 44 000.

Что получается в плане: оценка «1–30 строк» → `Nested Loops` с Seek/Key Lookup на каждую строку; по факту строк сотни тысяч — запрос работает минутами. После ночного обновления статистики запрос снова быстрый.

Лечение: обновлять статистику горячих таблиц чаще общего регламента; в MS SQL — новая модель оценки и `PERSIST_SAMPLE_PERCENT`; в PostgreSQL — пониженный `autovacuum_analyze_scale_factor` для больших таблиц.

### Коррелированные условия

`WHERE Организация = &Орг AND Склад = &Склад`: если склад однозначно принадлежит организации, настоящая селективность — как у одного склада. Оптимизатор этого не знает.

| | Как оценивает | Чем помочь |
|---|---|---|
| MS SQL, старая модель | Перемножает селективности: s₁ · s₂ · s₃ | Многоколоночная статистика: вектор плотности префикса `(A, B)` даёт число различных пар — работает для равенств по всем колонкам префикса |
| MS SQL, новая модель | «Экспоненциальное смягчение»: s₁ · s₂^(1/2) · s₃^(1/4) · s₄^(1/8), от самого селективного условия | То же; плюс фильтруемая статистика по проблемному значению |
| PostgreSQL | Перемножает селективности | `CREATE STATISTICS … (dependencies, mcv) ON a, b FROM t` + `ANALYZE` |

Пример из скрипта `08_statistics_plans.sql`: 100 складов в 10 организациях, `org = 3 AND sklad = 35` — по факту 10 000 строк. Без расширенной статистики оценка **~1 100**, после `CREATE STATISTICS` и `ANALYZE` — **~8 400**.

Виды расширенной статистики PostgreSQL: `ndistinct` (PG 10+, оценка `GROUP BY` по нескольким колонкам), `dependencies` (PG 10+, функциональные зависимости, только для равенств), `mcv` (PG 12+, частые комбинации значений), статистика по выражениям (PG 14+). Смотреть — в `pg_stats_ext`.

### Модель оценки кардинальности MS SQL

Модель определяется **уровнем совместимости** базы: до 110 — старая (CE 70), с 120 — новая, с изменениями в каждой версии. При переходе на новую версию SQL Server и повышении уровня совместимости часть планов меняется — в лучшую или худшую сторону. Безопасный порядок: включить Query Store, поднять уровень совместимости, сравнить и разобрать регрессии. Вернуть старую модель для всей базы — `ALTER DATABASE SCOPED CONFIGURATION SET LEGACY_CARDINALITY_ESTIMATION = ON` (SQL Server 2016+). Решение принимать по замерам на своей нагрузке.

### Применительно к 1С

- **Возрастающий ключ — почти везде:** `Период` в таблицах движений регистров (первая колонка кластерного индекса), `Дата` документов, `Период` регистров сведений. Типовая жертва — отчёт или проведение с отбором «за сегодня / с начала месяца» во второй половине дня. Помогает внеплановое обновление статистики по `_AccumRg…`, `_InfoRg…`, `_Document…` в течение дня.
- **Корреляция — тоже типична:** Организация + Склад, Номенклатура + Характеристика, Счёт + Субконто, условия RLS + отбор пользователя ([5.9](05-1c.md#59-как-ограничения-доступа-на-уровне-записей-rls-влияют-на-индексы-и-планы-запросов)).
- **Объекты статистики, созданные вручную** (`CREATE STATISTICS` в MS SQL или PostgreSQL), платформа не знает. Если реструктуризация пересоздаёт таблицу, они пропадут — держите скрипт и проверяйте после обновления конфигурации.
- **Диагностика:** в плане сравнить оценку и факт (`Estimated` и `Actual Number of Rows` в MS SQL, `rows=` и `actual rows=` в `EXPLAIN ANALYZE`). Расхождение в десятки раз на Seek по `Период` — сначала проверить свежесть статистики, а не создавать индекс.

> **Запомнить:** план выбирается по оценке строк из статистики. Пороги: MS SQL 500 + 20%, с 2016 — √(1000·n); PostgreSQL 50 + 10%, временные таблицы — никогда. Гистограмма MS SQL — до 200 шагов, только по первой колонке. Возрастающий ключ (`Период`) → новые строки вне гистограммы → оценка «1 строка» → `Nested Loops`. Корреляция условий → недооценка: в PostgreSQL — `CREATE STATISTICS`, в MS SQL — вектор плотности и новая модель оценки.

## 6.6. Что такое parameter sniffing и почему один и тот же запрос то пользуется индексом, то нет

> **Коротко.** MS SQL строит план параметризованного запроса по значениям параметров **первого** вызова и кладёт его в кэш. Следующие вызовы с другими значениями получают тот же план. Если данные распределены неравномерно, план под «маленькое» значение (Seek + Key Lookup) катастрофичен для «большого» (миллионы Lookup вместо Scan) — и наоборот. 1С передаёт параметры запроса (`&Параметр`) в MS SQL как параметры (`@P1`, `@P2` в тексте из ТЖ), поэтому эффект для неё типичен. Признаки: один и тот же запрос то быстрый, то медленный; «тормозит до утра» и проходит после ночного обновления статистики и очистки кэша. Лекарства: индекс, при котором один план хорош для любых значений (покрывающий — без Lookup), перестройка запроса, принудительный план через Query Store, в SQL Server 2022 — Parameter Sensitive Plan. В PostgreSQL похожий механизм — generic-план подготовленного запроса, но он включается, только если не дороже custom-планов.

### Как это происходит в MS SQL

1. Первый вызов `sp_executesql N'… WHERE _Fld123RRef = @P1'` с `@P1` = «маленькая организация». Оптимизатор подсматривает (sniffs) значение, по гистограмме оценивает 500 строк и выбирает Index Seek + Key Lookup.
2. План кэшируется по тексту запроса.
3. Вызов с `@P1` = «головная организация» (90% строк) берёт тот же план: Key Lookup на миллионы строк.
4. Если первым пришёл «большой» вызов, будет наоборот: Scan для всех, и «маленькие» запросы читают всю таблицу.

**Связь с индексами.** Выбор между Seek + Lookup и Scan — это и есть tipping point ([1.4](01-teoriya.md#14-почему-индекс-по-малоселективному-полю-может-не-использоваться-на-примере-булева-поля)): он зависит от оценки числа строк. Если индекс **покрывает** запрос ([1.6](01-teoriya.md#16-что-такое-покрывающий-индекс-и-зачем-нужны-включённые-столбцы-include)), Seek по нему хорош для любого числа строк: читается диапазон, пропорциональный результату, Lookup нет. План перестаёт зависеть от значения.

### Как распознать

- В фактическом плане (XML) у параметров есть `ParameterCompiledValue` (под какое значение строили) и `ParameterRuntimeValue` (с каким выполнили). Разные значения + большая ошибка оценки = sniffing.
- **Query Store:** у запроса несколько планов с очень разной длительностью; отчёты «Регрессировавшие запросы» и «Запросы с высокой вариативностью».
- `sys.dm_exec_query_stats`: большой разброс `min_elapsed_time`/`max_elapsed_time` и `min_rows`/`max_rows` у одного плана.

### Что можно сделать

| Способ | Что даёт | Для 1С |
|---|---|---|
| Индекс, при котором план не зависит от значения (покрывающий, подходящий порядок колонок) | Один план хорош для всех | Через метаданные: измерения регистра, «Индексировать», отбор в параметрах виртуальной таблицы |
| Перестройка запроса | Отбор во временную таблицу → дальше соединение по уже известному объёму | Да, основной способ разработчика |
| `OPTION (RECOMPILE)`, `OPTIMIZE FOR` в тексте | План под каждое значение / под заданное | Нет — текст запроса формирует платформа |
| Query Store: принудительный план (`sp_query_store_force_plan`, 2016+) | Закрепить хороший план | Да, силами администратора СУБД; пересматривать после обновлений конфигурации |
| Query Store hints (`sys.sp_query_store_set_hints`, SQL Server 2022) | Добавить `RECOMPILE` и другие подсказки без изменения текста | Да, силами администратора СУБД |
| Parameter Sensitive Plan (SQL Server 2022, уровень совместимости 160) | Несколько планов на один запрос в зависимости от объёма по параметру | Включается сам с уровнем совместимости 160 |
| `PARAMETER_SNIFFING = OFF` (database scoped configuration, 2016+) | План по «средней» плотности, без подсматривания | Меняет все запросы базы — только по замерам |
| Plan guide (`sp_create_plan_guide`) | Подсказка по точному тексту запроса | Хрупко: тексты 1С меняются (имена `#tt`, порядок полей) |

Очистка кэша (`DBCC FREEPROCCACHE` после обновления статистики в регламенте 1С, [6.1](#61-каков-регламент-обслуживания-индексов-и-статистики-для-баз-1с-на-ms-sql-и-на-postgresql)) заодно сбрасывает «прилипшие» планы. Но это лечит симптом до следующего неудачного первого вызова.

### PostgreSQL: custom- и generic-план

Подготовленный запрос (`PREPARE`, расширенный протокол драйвера) с параметрами `$1, $2…`:
- **Первые 5 выполнений** — **custom-план**, построенный под конкретные значения.
- Дальше PostgreSQL строит **generic-план** без знания значений (оценки по «средним» значениям) и использует его, если он **не дороже** средней стоимости custom-планов. Иначе продолжает строить custom.
- Управление — `plan_cache_mode` (PG 12+): `auto` (по умолчанию), `force_custom_plan`, `force_generic_plan`. Счётчики планов — `pg_prepared_statements.generic_plans/custom_plans` (PG 14+). Посмотреть generic-план без выполнения — `EXPLAIN (GENERIC_PLAN)` (PG 16+).

В скрипте `08_statistics_plans.sql`: при перекосе 1% / 99% generic-план (оценка ~500 000 строк) дороже custom, и PostgreSQL остаётся на custom-планах; для поиска по уникальному ключу с шестого выполнения включается generic. То есть защита от «прилипшего» плана встроена, но не абсолютна: если «средняя» стоимость случайно близка, generic закрепится и для нетипичных значений.

### Применительно к 1С

- **MS SQL:** параметры `&Параметр` приходят в СУБД параметрами `@P1…`, а значения, записанные прямо в тексте запроса (`ЗНАЧЕНИЕ(Перечисление.…)`, числовые и строковые константы), — литералами. Sniffing возможен по каждому параметру.
- **Где перекос типичен:** организация (головная против мелких), склад, вид операции, статус документа, «пустая ссылка» в отборе, параметры RLS у разных пользователей ([5.9](05-1c.md#59-как-ограничения-доступа-на-уровне-записей-rls-влияют-на-индексы-и-планы-запросов)). Отсюда жалоба «у одного пользователя/организации отчёт летает, у другой — нет».
- **PostgreSQL:** поведение зависит от того, как платформа передаёт значения параметров. Если они приходят в тексте запроса литералами (видно в событии `DBPOSTGRS` ТЖ), план строится заново под каждое значение и generic-плана нет. Если параметрами `$1…` — работает схема custom/generic. Проверьте по ТЖ своей базы.
- **Порядок разбора:** ТЖ / Query Store → тот же запрос с разными значениями → сравнить планы → решить индексом или перестройкой запроса. Принудительный план — когда изменить запрос нельзя (типовая конфигурация).

> **Запомнить:** MS SQL кэширует план, построенный под значения первого вызова. При перекосе данных Seek + Lookup под «малое» значение губит «большое» и наоборот. 1С передаёт `&Параметры` как `@P1…` — эффект типичен. Распознать: `ParameterCompiledValue` ≠ `ParameterRuntimeValue`, несколько планов в Query Store. Лечить: покрывающий индекс (план перестаёт зависеть от значения), временные таблицы, принудительный план / hints в Query Store, PSP в 2022. PostgreSQL: первые 5 выполнений — custom, дальше generic, только если он не дороже.
